## 확정 정책

- 근로자 본인만 사용한다. 회원 ID는 세션의 FarmPrincipal에서 가져온다.
- 현재 DB의 회원 존재·근로자 역할도 확인한다. 고용주·삭제 계정·역할 변경 계정은 거절한다.
- 회원당 현재 계좌 최대 1개, 미등록 허용.
- 은행 코드는 숫자 3자리 문자열, 계좌는 ASCII 하이픈을 제거한 숫자 1~30자리다. 앞자리 0을 보존한다.
- 예금주명은 앞뒤 공백을 제거하고 빈 값·100자 초과를 거절한다.
- PUT의 세 계좌 필드와 version은 모두 필수다. 문자열 필드는 JSON 문자열, version은 0 이상의 JSON 정수만 받는다.
- 마스킹은 5자리 이상이면 마지막 4자리만 표시하고, 4자리 이하면 모두 가린다.
- 오래된 버전의 PUT은 409다. DELETE는 현재 등록된 계좌의 버전이 달라지면 409, 현재 미등록이면 오래된 버전이어도 204다.
- 409 이후에는 GET으로 최신 정보를 확인하고 사용자가 다시 저장해야 한다. 자동 재저장하지 않는다.
- DELETE도 version 누락·형식 오류 등 유효하지 않은 요청은 400이다. 이미 미등록인 경우의 204는 인증·권한·CSRF·입력 검사를 통과한 요청에 적용한다.

## 공통 인증

기존 농업 로그인 세션(FARMSESSION)을 사용한다. 내부 보험용 Bearer 토큰으로 호출하는 경로가 아니다.
PUT·DELETE 직전 GET /api/auth/csrf에서 받은 토큰을 같은 세션의 헤더로 전달한다.
기존 인증·CSRF 처리 순서를 유지하며, 특히 CSRF가 없는 쓰기 요청은 로그인 검사보다 먼저 403이 될 수 있다.
성공 및 컨트롤러 업무 오류 응답에는 Cache-Control: no-store를 적용한다.

## 1. 조회

GET /api/me/salary-account

200 (등록됨):

```json
{
  "registered": true,
  "bankCode": "020",
  "maskedAccountNumber": "********0400",
  "accountHolderName": "TEST WORKER",
  "version": 0
}
```

200 (미등록):

```json
{
  "registered": false,
  "bankCode": null,
  "maskedAccountNumber": null,
  "accountHolderName": null,
  "version": 0
}
```

version은 계좌 등록 여부와 관계없이 제공한다. 기존 V9 계좌도 V10 적용 직후에는 0에서 시작한다.
1자리 번호는 *, 4자리는 ****, 5자리 12345는 *2345다.
번호를 응답에 표시할 때만 서버 내부에서 AES-GCM 인증 복호화·숫자 형식 확인 후 마스킹한다.
복호화한 원문을 반환하거나 로그에 넣지 않는다. 키 불일치·암호문 변조는 503으로 처리한다.
미등록 조회는 계좌 암호화 키 없이도 가능하다.

## 2. 등록·교체

PUT /api/me/salary-account
Content-Type: application/json
X-CSRF-TOKEN: 발급받은 토큰

```json
{
  "bankCode": "020",
  "accountNumber": "1002-0030-0400",
  "accountHolderName": "TEST WORKER",
  "version": 0
}
```

200: 조회와 같은 형식이며 성공한 새 version을 반환한다.
미등록이면 신규 등록, 등록 상태면 전체 계좌 교체다. 마스킹 문자열을 저장 요청으로 보내면 안 된다.
유효한 PUT은 같은 값을 보내더라도 버전을 증가시킨다. 이전 버전으로 재전송한 요청은 409다.
교체 시 created_at을 보존하고 updated_at은 UTC 마이크로초로 갱신한다.

## 3. 해제

DELETE /api/me/salary-account?version=1
X-CSRF-TOKEN: 발급받은 토큰

본문은 사용하지 않는다. version은 조회 당시 버전이다.
성공 시 204이며 응답 본문은 없다. 새 버전이 필요하면 GET으로 다시 조회한다.
등록된 계좌를 해제하면 버전을 증가시킨다. 미등록 상태의 반복 해제는 204이며 버전을 증가시키지 않는다.
해제는 계좌 복호화를 요구하지 않는다. 회원·근무·보험 변경 기록은 삭제하지 않는다.

## 버전과 저장 흐름

SalaryAccountApi → SalaryAccountService → MemberRepository / MemberSalaryAccountRepository → SalaryAccountCrypto

- V10에서 member.salary_account_version BIGINT NOT NULL DEFAULT 0을 추가한다.
- 회원 행은 계좌가 없거나 해제돼도 남으므로 버전이 0으로 되돌아가지 않는다.
- PUT·DELETE는 JPA의 PESSIMISTIC_WRITE로 회원 행을 잠그고 현재 역할·버전을 확인한다.
- 계좌 변경과 회원 버전 증가를 같은 트랜잭션에서 flush한다. 실패하면 함께 롤백하도록 구성했다.
- 최초 등록 경합과 해제 후 재등록도 같은 회원 잠금을 사용한다.
- GET은 REPEATABLE_READ 트랜잭션에서 회원 버전과 계좌를 같은 스냅샷으로 읽도록 구성했다.
- 실제 MySQL 잠금·스냅샷·롤백 동작은 아직 실행 검증하지 않았다.
- V1~V9 파일과 기존 계좌 암호문·기존 회원 정보는 수정하지 않는다. V10은 신규 버전 컬럼만 추가한다.
- 기존 가입·이관 데이터의 키를 새로 생성하거나 교체하지 않는다. 앱 및 회원 매핑을 사용하는 도구는 V10 적용 후 사용한다.

## 실패 응답

```json
{
  "code": "SALARY_ACCOUNT_VERSION_CONFLICT",
  "message": "급여 계좌가 변경되었습니다. 최신 정보를 확인한 뒤 다시 요청해 주세요."
}
```

| HTTP | 코드 | 조건 |
| --- | --- | --- |
| 400 | INVALID_REQUEST | 필수값·형식·버전 오류 |
| 401·403 | 기존 인증·CSRF 처리 | 로그인 필요·CSRF 오류 |
| 403 | WORKER_ROLE_REQUIRED | 고용주·삭제 계정·현재 DB 역할이 근로자가 아님 |
| 409 | SALARY_ACCOUNT_VERSION_CONFLICT | PUT 또는 등록된 계좌 DELETE의 오래된 버전 |
| 415 | Spring 기본 처리 | PUT의 Content-Type이 application/json이 아님 |
| 503 | SERVICE_UNAVAILABLE | 계좌 키·암호문 처리 오류·일시적 DB 장애 |
| 500 | INTERNAL_SERVER_ERROR | 기타 내부 오류 |

Content-Type 415는 컨트롤러 선택 전에 발생할 수 있으므로 code/message 업무 오류 형식을 보장하지 않는다.
오류에 계좌번호·키·암호문·SQL·내부 예외 원문을 포함하지 않는다.

## farm-demo 급여 계좌 화면

- GET /demo/salary-account는 farm-demo에서만 등록되는 간이 화면이다. /demo/login에서 근로자로 로그인하면 이동 링크를 표시한다.
- 새 데모 저장 API를 만들지 않고 실제 GET·PUT·DELETE /api/me/salary-account를 호출한다.
- 처음 열 때와 사용자가 최신 계좌 조회를 눌렀을 때 로그인 계정·최신 계좌·version을 조회한다.
- PUT·DELETE 직전 같은 세션의 새 CSRF를 받고 로그인 회원이 화면의 계정과 같은지 다시 확인한다.
- 은행 선택 전 계좌번호 입력을 잠근다. 은행 선택·기타 코드·확인된 대표 하이픈 형식은 기존 signup 안내 기준을 사용한다. 은행별 길이를 서버 규칙으로 강제하지 않는다.
- 조회 영역은 마스킹된 번호만 표시하고, 새 계좌 입력 영역에는 사용자가 입력 중인 전체 번호를 표시한다. 마스킹된 기존 번호를 입력 칸에 복사하지 않는다.
- PUT에는 조회 당시 version을 자동으로 포함한다. DELETE는 조회 당시 version을 쿼리로 자동 전송한다.
- PUT 성공 응답으로 새 버전을 기억한다. DELETE의 204 이후에는 GET으로 새 상태·버전을 읽는다. 해제 성공과 후속 조회 실패는 구분해 표시한다.
- 다른 창의 변경을 자동 반영하지 않는다. 409 이후에는 저장·해제를 잠그고 최신 계좌 조회를 요구한다. 자동 재시도는 하지 않는다.
- 네트워크 오류 등으로 처리 결과를 알 수 없으면 최신 조회 전 추가 쓰기를 막는다.
- 동일 창의 중복 전송을 막고, 계정 변경·페이지 이탈 때 입력 번호·조회 결과·버전을 지운다. 뒤로 돌아올 때 새로 조회하며, 단순한 탭 전환은 버전을 바꾸지 않는다.
- 요청 본문·계좌 원문·CSRF를 결과·로그·URL·브라우저 저장소에 넣지 않는다. 화면에는 허용된 마스킹 응답과 고정 업무 오류만 textContent로 표시한다.
- user-web과 실제 제품 화면은 수정하지 않는다.

### 수동 확인 순서

1. 원래 wonday/farm-api에서 기존 .env·계좌 키를 유지하고 farm-demo로 서버를 재시작한다. 앱 시작 시 신규 V10 적용이 필요하다. 이 작업에서 서버·DB 적용은 실행하지 않는다.
2. localhost:18081/demo/login에서 근로자 계정으로 로그인한 뒤 급여 계좌 링크로 이동한다. 실행 포트가 다르면 주소도 맞춘다.
3. 최신 계좌 조회의 HTTP 200·등록 여부·조회 버전을 확인한다.
4. 은행·가상 계좌·예금주를 입력해 등록·교체한다. HTTP 200과 마스킹·증가한 버전을 확인한다.
5. 가상 숫자 12345 → *2345, 1234 → ****, 1 → *를 확인한다. 대표 표시 하이픈이 붙어도 숫자 개수 기준으로 마스킹한다.
6. 계좌 해제의 HTTP 204와 후속 미등록 상태를 확인한다. 다시 해제해도 HTTP 204다.
7. 두 창에서 같은 근로자 계정으로 이 화면을 열고 양쪽 모두 최신 계좌를 조회한다.
8. 창 A에서 저장한 뒤 창 B는 조회하지 않고 저장한다. 창 B의 HTTP 409·오류 코드·최신 조회 안내를 확인한다.
9. 창 B에서 최신 계좌를 조회하고 내용을 확인한 뒤 다시 저장한다. HTTP 200을 확인한다.
10. 해제 충돌은 양쪽을 다시 조회한 뒤 창 A에서 다시 교체하고, 창 B는 조회하지 않고 해제를 누른다. 현재 계좌가 등록돼 있다면 HTTP 409다.
11. 이미 미등록인 경우의 예외는 양쪽에서 등록된 상태를 조회한 뒤 A에서 해제하고, B에서 오래된 버전으로 해제한다. 현재 미등록이므로 HTTP 204다.

이 절은 확인 방법이며 실제 수동 성공 결과가 아니다. 테스트·브라우저·서버·DB·커밋·푸시는 실행하지 않는다.

# CHANGE-01·02 시작 전 개인별 확정 근무 취소

## 범위와 요청 흐름

고용주가 본인 공고의 개인별 확정 근무 하나를 취소한다. 날짜 전체 모집 취소(JOB-07), 조기 종료(CHANGE-03), 사유 보완(CHANGE-04), 날짜 전체 작업 취소(CHANGE-05)와 구분한다.

`WorkCancellationApi` → `CancellationInput`·`WorkCancellationService` → `WorkChangeRecorder.cancelBeforeStart` → 기존 원본·보험 변경 버전 저장 → 응답 순서다.

- 역할은 세션뿐 아니라 현재 DB 회원 정보로 다시 확인한다.
- 타인 소유와 없는 근무는 모두 404다. 고용주 ID·근로자 ID·취소 시각을 요청으로 받지 않는다.
- 정식 사용자 API는 기본 프로필에서도 제공하고, farm-demo는 시연 데이터 준비에만 사용한다.
- 근로자 본인 취소·재확인 미응답 자동 취소는 이번 범위에 포함하지 않는다.

## 요청

```http
POST /api/work-assignments/7001/cancellation
Content-Type: application/json
X-CSRF-TOKEN: {로그인 후 새로 발급받은 토큰}
Cookie: FARMSESSION={고용주 로그인 세션}
```

```json
{
  "reasonCode": "WEATHER",
  "weatherReasonCode": "RAIN",
  "reasonDetail": "  강수로 작업을 취소합니다.  "
}
```

| 필드 | 규칙 |
|---|---|
| reasonCode | WEATHER / FARM_CIRCUMSTANCES / OTHER 중 필수 |
| weatherReasonCode | WEATHER면 RAIN / WIND / HEAT / OTHER 중 필수. 나머지 사유는 생략 또는 null |
| reasonDetail | 선택. 앞뒤 공백 제거 후 빈 값은 null. 유니코드 코드 포인트 최대 500개 |

설명의 중간 공백·줄바꿈은 보존하고 길이에 포함한다. 양 끝의 공백·탭·줄바꿈·유니코드 공백은 제거한다. 예를 들어 이모지 😀 500개는 Java UTF-16 길이 1,000이어도 500 코드 포인트이므로 허용하고, 501개는 400이다. 여러 코드 포인트를 조합한 이모지는 조합 수에 따라 여러 자로 계산한다. 설명이 길어도 임의로 잘라 저장하지 않는다.

각 필드는 JSON 문자열 또는 허용된 null만 받는다. 숫자·불리언·배열·객체의 문자열 자동 변환은 거절한다. 사유 코드는 명시된 대문자와 정확히 일치해야 한다.

## 취소 가능 시점과 재요청

- 신규 취소는 기존 취소·조기 종료·완료가 없는 확정 근무만 허용한다.
- 약정의 agreedStartAt·agreedTimeZone으로 시작 시각을 계산한다. 현재 공고의 수정된 시간으로 대체하지 않는다.
- 잠금 대기와 상태 조회가 끝난 서버 현재 시각이 약정 시작보다 전이어야 한다. 정확히 같은 시각부터 신규 취소는 409다.
- 모집 중·일시중단·마감 상태는 개인별 취소 가능 여부를 제한하지 않는다.
- 이미 취소되어 있으면 정규화한 사유·기상 세부 사유·설명을 모두 비교한다.
- 같으면 시작 시각 이후라도 200으로 기존 결과를 반환한다. 시계·버전·발행 순번을 갱신하지 않는다.
- 다르면 409 CANCELLATION_REASON_CONFLICT다. 이 API에서 기존 설명을 수정하거나 새 변경 버전을 만들지 않는다.
- 동일 내용 비교는 현재 저장된 취소 기록을 기준으로 한다. 후속 사유 보완에서 내용이 달라졌으면 이전 내용을 재전송해 덮어쓸 수 없다.
- 이전 회차의 취소 후 재지원했더라도 기존 확정 근무의 취소 결과는 그대로 유지한다.

## 성공 응답

최초 취소와 같은 내용 재요청 모두 200 OK, Cache-Control: no-store다.

```json
{
  "assignmentId": 7001,
  "changeId": 9001,
  "changeType": "CANCELLED",
  "reasonCode": "WEATHER",
  "weatherReasonCode": "RAIN",
  "reasonDetail": "강수로 작업을 취소합니다.",
  "effectiveAt": "2026-12-02T08:30:00+09:00",
  "recordedAt": "2026-12-02T08:30:00+09:00",
  "updatedAt": "2026-12-02T08:30:00+09:00",
  "sourceVersion": "1"
}
```

최초 취소의 세 시각은 동일한 서버 시각으로 저장한다. DB에는 UTC·마이크로초로 저장하고 약정 시간대의 오프셋으로 반환한다. GMT+9 약정이면 +09:00이다. 재요청은 변경 ID·사유·버전·시각을 새로 만들지 않고 저장된 결과를 읽는다.

지원 상태를 미선정으로 바꾸거나 확정 근무·약정을 삭제하지 않는다. 동일 날짜의 다른 사람도 변경하지 않는다. 지원·명단·내역 조회는 기존 work_change의 CANCELLED 집계를 사용한다. 취소했다고 모집 상태를 자동 재개하거나 근로자를 다시 선정하지 않는다.

## 실패 응답

```json
{
  "code": "CANCELLATION_REASON_CONFLICT",
  "message": "이미 기록된 취소 내용과 다릅니다. 사유 보완 기능을 이용해 주세요."
}
```

| HTTP | 코드 | 조건 |
|---|---|---|
| 400 | INVALID_REQUEST | 양수가 아닌 ID·잘못된 ID 형식, 본문 누락·형식 오류, 사유 조합 오류, 설명 500 코드 포인트 초과 |
| 401 | 기존 인증 응답 | 로그인 세션 없음 |
| 403 | EMPLOYER_ROLE_REQUIRED | 근로자 또는 현재 DB 역할이 고용주가 아님 |
| 403 | 기존 CSRF 응답 | CSRF 누락·오류 |
| 404 | WORK_ASSIGNMENT_NOT_FOUND | 근무 없음 또는 다른 고용주의 근무 |
| 409 | WORK_ALREADY_STARTED | 신규 취소 요청이 약정 시작 시각에 도달하거나 그 이후 |
| 409 | WORK_ALREADY_EARLY_ENDED | 기존 조기 종료 기록 있음 |
| 409 | WORK_ALREADY_COMPLETED | 기존 완료 기록 있음 |
| 409 | CANCELLATION_REASON_CONFLICT | 기존 취소와 정규화한 사유·세부 사유·설명이 다름 |
| 409 | WORK_STATE_CONFLICT | DB 무결성 충돌 |
| 415 | INVALID_REQUEST | JSON으로 읽을 수 없는 Content-Type |
| 503 | SERVICE_UNAVAILABLE | 필수 약정 시간대·시작 시각 해석 불가, DB 장애·잠금 시간 초과 등 |
| 500 | INTERNAL_SERVER_ERROR | 기타 내부 오류 |

경로 ID는 양수의 10진 숫자 문자열만 허용한다. 소수·부호·공백·지수 표기·범위 초과를 거절한다. 취소 API의 성공·컨트롤러 오류 응답에는 no-store를 적용하고, 인증·CSRF 오류는 기존 보안 체인 응답을 유지한다. 서버 전용 보험 Bearer 토큰은 고용주 세션·CSRF를 대신하지 않는다.

## 저장과 보험 주기 조회

기존 WorkChangeRecorder에 사용자 취소 전용 진입점을 추가했다. 기존 recordValidatedChange·reviseReason의 호출 규격과 demo 준비 동작은 유지한다.

1. 현재 고용주 역할·소유권을 확인한다.
2. 근로자의 보험 변경 스트림 행을 보장하고 잠근다.
3. 확정 근무 행 → 변경 행 순서로 잠근다.
4. 기존 완료·조기 종료·취소와 동일 내용 재요청을 검사한다.
5. 신규 취소의 약정 시작 시각을 검사한다.
6. work_change를 저장하고 발행 순번을 증가시켜 work_change_version을 함께 저장한다.

원본·버전·순번 증가는 같은 READ_COMMITTED 트랜잭션이다. 버전 저장이 실패하면 원본도 롤백되도록 구성했다. 완료는 같은 확정 근무 행을 잠그므로 취소와 완료가 함께 기록되지 않도록 구성했다. 동일 요청 재시도에는 새 버전이나 순번을 발행하지 않는다. 실제 MySQL 경합·롤백은 아직 실행 검증하지 않았다.

모든 사유의 변경 기록을 기존 보험 주기 조회에 제공한다. WEATHER라도 지급 여부를 농업 서버가 판정하지 않는다. 농장 사정·개인 사정의 제외와 위험 지수·보험금 계산·심사는 보험 서버의 역할이다. EVENT_OUTBOX·RabbitMQ·취소 푸시는 추가하지 않는다.

새 테이블·컬럼·마이그레이션은 필요하지 않다. 기존 적용된 마이그레이션과 과거 데이터를 변경하지 않는다. 시간대나 시작 시각이 누락된 기존 약정은 현재 공고로 보완하지 않고 신규 취소를 503으로 거절한다.

## farm-demo 시연 데이터 준비

이전에 요청한 기능별 더미 데이터 준비를 위해 다음 endpoint를 제공한다. `/demo/work-cancellation` 간이 화면에서 버튼으로 준비·취소·재요청을 확인할 수 있다.

```http
POST /demo/api/work-cancellation/fixtures
X-CSRF-TOKEN: {고용주 로그인 후 새로 발급받은 토큰}
Cookie: FARMSESSION={고용주 로그인 세션}
```

- farm-demo에서만 활성화한다. 고용주 본인 세션·현재 DB 역할·CSRF를 확인한다.
- 기존 WORK-02 시연 준비 서비스를 재사용해 본인 고용주와 demo-worker의 가상 공고를 준비한다. demo-worker 계정이 필요하다.
- 그 준비 응답의 공고 ID와 사례로만 확정 근무를 준비한다. 자정 이후 날짜를 다시 읽지 않는다.
- 준비 응답 직후 본인 소유 공고를 PESSIMISTIC_WRITE로 먼저 잠근다. 루프의 약정·지원·일정 조회와 선정 호출보다 앞서 획득하고 준비 트랜잭션이 끝날 때까지 유지한다. 기존 확정 사례와 미선정 사례가 섞인 재사용에서도 선정 서비스와 공고 선잠금 순서를 맞춘다.
- 일반 정상·다른 정상 근무·일시중단 사례는 실제 선정 서비스를 통해 확정한다.
- 시작 경과 사례만 시연용 과거 약정을 생성한다. 사용자 선정 API의 시작 전 제한은 그대로 둔다.
- 기존 취소·조기 종료·완료 사례는 재사용하고 초기화하지 않는다.
- 이미 취소한 정상 사례를 다시 CONFIRMED로 바꾸지 않는다. 같은 날 다시 준비해도 앞서 실행한 결과가 유지된다.
- 기존 WORK-02 시연 공고를 함께 사용하므로, 선정 demo에서도 이번 준비로 확정된 상태가 보일 수 있다.
- 새 가상 공고 준비는 201, 기존 공고 재사용은 200이다. 이 상태코드는 정식 취소의 200 정책과 별개다.

응답 cases의 assignmentId를 정식 취소 API에 사용하고 suggestedRequest를 본문으로 사용한다. 다른 사유 409는 해당 요청의 설명 또는 사유를 바꿔 확인한다.

| scenario | 확인 내용 |
|---|---|
| NORMAL | 최초 200 → 동일 내용 재요청 200 → 다른 내용 409 |
| STALE_VERSION | 별도 정상 근무가 그대로 유지되는지 확인 |
| PAUSED | 일시중단 날짜에서도 개인별 취소 가능 |
| STARTED | 시작 후 최초 취소 409 |
| CANCELLED | 저장된 사유로 기존 취소 재요청 200 |
| EARLY_ENDED | 조기 종료된 근무 취소 409 |
| COMPLETED | 완료된 근무 취소 409 |

설명 501자·기상 세부 사유 누락은 아직 취소하지 않은 정상 사례에서 확인할 수 있다. 기존 취소의 재요청 내용은 임의로 바꾸지 않고 응답의 suggestedRequest를 사용한다. 근로자로 로그인하면 고용주 취소·시연 준비는 모두 403이다.

## farm-demo 간이 화면 확인 순서

### 실행과 로그인

1. 원래 wonday 폴더의 work-cancel 브랜치에서 기존 farm-demo 실행 설정으로 서버를 재시작한다.
2. Docker MySQL이 켜져 있어야 한다. 기존 .env·암호화 키 설정을 그대로 사용한다.
3. 브라우저에서 http://localhost:18081/demo/login 을 연다. 실제 실행 포트가 다르면 그 포트를 사용한다.
4. 고용주 계정으로 로그인한다. 처음에는 demo-employer를 사용하면 쉽다.
5. 로그인 뒤 「개인별 시작 전 취소 · 재요청 확인」 링크를 누른다. 직접 /demo/work-cancellation 으로 들어가도 된다.

화면은 farm-demo에서만 제공한다. 화면의 모든 쓰기는 기존 세션으로 실제 API에 요청한다. POST마다 새 CSRF 토큰을 받아 헤더에 넣으며 화면·요청 기록·웹 저장소에 토큰을 표시하거나 저장하지 않는다. 서버 전용 Bearer 토큰은 사용하지 않는다.

### 시연 데이터와 사례 선택

1. 「1. 시연 데이터 준비 · 사례 선택」에서 「취소 시연 데이터 준비」를 누른다.
2. 「시연 준비 HTTP 201」 또는 「시연 준비 HTTP 200」을 확인한다. 이는 데이터 준비 응답이며 취소 결과가 아니다.
3. 사례 표가 나타나고 첫 정상 사례가 자동으로 선택된다. 직접 고르려면 표 오른쪽 「이 사례 선택」을 누른다.
4. 「2. 선택한 근무 · 취소 사유」에 공고·일정·확정 근무 ID와 약정 시작 일시가 보이는지 확인한다.
5. 「DB 재조회: … 정상 확정」을 확인한다. 저장 상태 GET이 실패해도 사례 선택과 취소 버튼은 유지된다.

준비는 기존 데이터를 초기화하지 않는다. 정상 사례가 이미 취소 상태라면 그 사례의 첫 요청도 기존 결과 200이다. 최초 취소를 다시 보려면 현재 상태가 정상 확정인 다른 사례(「다른 정상 확정 근무의 상태 유지 확인」 또는 「일시중단 날짜의 개인별 취소」)를 선택한다.

### 최초 취소 200

1. 정상 확정 사례를 선택한다.
2. 취소 사유 「기상」, 기상 세부 사유 「강수」를 확인한다. 설명은 수정하거나 비워도 된다.
3. 「3. 최초 취소 · 재요청 · 다른 사유 충돌」에서 「취소 요청 보내기」를 누른다.
4. 「4. 최근 취소 API 응답」에 HTTP 200이 나오는지 확인한다.
5. 변경 ID·변경 버전·취소 확정 일시·최초 저장 일시·최종 수정 일시를 확인한다.
6. 사례 표와 「DB 재조회」가 「시작 전 취소」로 바뀌는지 확인한다.
7. 요청 본문·응답 원문은 각 접힌 항목을 눌러 확인한다. 설명 앞뒤 공백은 응답에서 제거되고 빈 값은 null이다.

### 같은 내용 재요청 200

1. 같은 사례를 유지한 상태에서 「같은 내용으로 재요청 · 200 확인」을 누른다.
2. HTTP 200과 「기존 결과 유지 확인」 문구를 확인한다.
3. 변경 ID·버전·세 시각이 이 화면에서 처음 받은 성공 응답과 같은지 확인한다.

이 버튼은 직전 성공한 요청 본문을 복사해 보낸다. 사유 입력 칸을 수정해도 재요청 버튼의 본문은 바뀌지 않는다. 기존 취소 사례에서는 응답의 suggestedRequest를 사유 입력 칸에 채우므로 첫 요청부터 저장된 결과를 확인할 수 있다.

### 다른 사유 409

1. 동일 사례에서 취소 200을 받은 상태를 유지한다.
2. 「다른 사유로 재요청 · 409 확인」을 누른다.
3. HTTP 409, CANCELLATION_REASON_CONFLICT와 사유 보완 안내를 확인한다.
4. 이 버튼은 직전 성공 요청의 사유만 유효한 다른 사유로 바꾸고 기상 세부 사유는 null로 맞춰 전송한다.
5. 이전 성공의 변경 ID·버전·세 시각이 화면에 남아 있는지 확인한다.
6. 별도 DB 재조회가 여전히 「시작 전 취소」인지 확인한다.
7. 다시 「같은 내용으로 재요청 · 200 확인」을 누르면 앞선 성공 요청으로 200을 받을 수 있다.

### 추가 오류 사례

- 「시작 후 최초 취소 거절 409」 선택 → 「취소 요청 보내기」 → WORK_ALREADY_STARTED.
- 「조기 종료 근무 취소 거절 409」 선택 → 요청 → WORK_ALREADY_EARLY_ENDED.
- 「완료 근무 취소 거절 409」 선택 → 요청 → WORK_ALREADY_COMPLETED.
- 취소 사유가 기상인데 세부 사유를 「선택하지 않음」으로 변경 → 요청 → 400 INVALID_REQUEST.
- 설명을 501 코드 포인트로 입력 → 화면의 길이 표시 확인 → 요청 → 400 INVALID_REQUEST.
- 500자 오류 확인을 위해 textarea에 HTML maxlength를 두지 않았다. 브라우저가 먼저 잘라 서버 검증을 가리는 것을 피한다.

### 응답 표시와 계정 전환

- 취소 POST 응답과 보조 상태 GET 응답을 별도 영역에 표시한다. GET 오류가 취소 결과·선택·재요청 정보를 지우지 않는다.
- 상태 조회의 completedAt은 화면에서 「완료 일시」로 표시한다.
- 화면에서 처음 받은 취소 200을 비교 기준으로 사용한다. DB 최초 생성 여부를 화면만 보고 새로 판정하지 않는다.
- 요청 전후 /me로 계정과 역할을 확인한다. 다른 창에서 계정이 바뀌면 이전 사례·요청·응답을 지우고 다시 준비하도록 한다.
- pagehide 시 진행 요청을 중단하고 화면 데이터를 지운다. 통신 오류 때 취소 POST를 자동 재전송하지 않는다.
- 사용자 데이터는 textContent로 표시하며 HTML로 삽입하지 않는다. 요청 기록은 최근 12개로 제한하고 CSRF 발급 요청은 기록하지 않는다.


## 검증 범위

사용자 요청에 따라 테스트 실행·서버 실행·실제 DB 작업·커밋·푸시는 하지 않는다. `compileJava --offline --no-daemon --console=plain` 컴파일은 성공했고 diff 공백 검사도 통과했다. HTTP·Security·CSRF·실제 MySQL·동시 요청·보험 서버 상호 호출 검증은 별도로 필요하다. 과거 선정 기능의 테스트 통과 수치를 이 취소 API의 검증 결과로 사용하지 않는다.


## 취소 시연 준비 잠금 순서 리뷰 보완

기존에는 재사용 사례의 약정을 먼저 잠근 뒤 다른 사례의 선정에서 공고를 잠글 수 있어, 공고를 먼저 잡는 선정 재요청과 순환 대기가 가능했다. 준비 응답의 고용주 소유 공고 잠금을 루프 앞에서 획득하도록 변경했다. 준비된 공고를 잠글 수 없으면 503으로 종료하고 하위 조회·선정을 진행하지 않는다.

회귀 테스트는 기존 확정 NORMAL과 미선정 STALE_VERSION이 섞인 사례의 호출 순서, 시작 경과 사례의 공고 선잠금, 공고 잠금 실패 시 하위 처리 중단을 검사하도록 보완했다. 이번 수정 후 테스트는 실행하지 않았다. mock 호출 순서는 실제 MySQL의 두 트랜잭션 경합을 증명하지 않으며, 준비와 선정 재요청을 교차 실행하는 검증은 별도로 필요하다.

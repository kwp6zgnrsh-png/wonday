# 작업지 좌표 저장·조회 API

## 이번 구현 범위

공고 등록·조회와 보험 확정 근무 상세 응답에 좌표를 연결한다. 제품의 지도 화면·카카오 지도 SDK·주소 검색은 구현하지 않는다. 주소는 고용주가 직접 입력하고, 좌표는 프론트에서 사용자가 독립적으로 지정한 실제 작업지 핀 좌표를 전달한다. 서버는 입력의 숫자 형식·범위를 검증하며, 좌표만으로 사용자의 핀 선택 과정을 입증하지는 않는다. 개인 확인용으로는 별도의 farm-demo 좌표 입력·등록·조회 화면을 제공한다.

## 공고 등록

기존 `POST /api/job-postings`의 고용주 세션·CSRF·일정 전체 검증·트랜잭션을 유지한다. 신규 요청은 주소와 양쪽 좌표가 모두 필수다.

전체 요청 예시(실행 결과 아님):

```json
{
  "title": "사과 수확 근로자 모집",
  "description": "시연용 공고입니다.",
  "cropCode": "FT01060100060100",
  "workTypeCode": "0058",
  "workLocation": "고용주가 직접 입력한 실제 작업지 주소",
  "latitude": 37.12345678,
  "longitude": 127.12345678,
  "timeZone": "GMT+9",
  "headcount": 2,
  "dailyWage": 120000,
  "schedules": [{
    "workDate": "2026-12-02",
    "plannedStartAt": "2026-12-02T08:00:00",
    "plannedEndAt": "2026-12-02T17:00:00",
    "breakStartAt": null,
    "breakEndAt": null
  }]
}
```

- 위도 원본 범위: -90 이상 90 이하. 경도 원본 범위: -180 이상 180 이하.
- JSON 정수·소수 숫자를 허용한다. 숫자 문자열·배열·객체·boolean은 `400 INVALID_REQUEST_BODY`다.
- 누락·null·원본 범위 위반은 HTTP Bean Validation에서 `400 INVALID_JOB_POSTING`과 해당 `field`로 반환한다.
- 엔티티 생성 경로도 원본 범위를 다시 확인하며 잘못된 값은 저장 전에 `INVALID_WORK_LOCATION` 예외로 거절한다.
- 원본 범위 검사 뒤 소수점 6자리 HALF_UP으로 반올림한다. DB에 반올림을 맡기거나 먼저 double로 변환하지 않는다.
- 절댓값이 `0.0000005` 미만이면 수학적으로 동일한 결과인 `0.000000`을 바로 반환한다. 극소 지수 입력의 과도한 `setScale` 연산을 피하며, 정확히 `±0.0000005`인 경계부터는 기존 `setScale(6, HALF_UP)`을 적용한다.
- D-1 수정 후 독립 단위 재검증에서 관련 3개 클래스 180개가 모두 통과했다. 극소 지수 입력·HALF_UP 경계·원본 범위 검사·JSON 정밀도 유지와 정규화를 확인했다. 자세한 범위와 측정 결과는 [D-1 재검증 보고서](verification/2026-11-26-job-location-d1-recheck/VERIFICATION_REPORT.md)를 참고한다. 수정 전 226개·331개 결과와 합산하지 않으며 실제 HTTP 성능·DB·통합 테스트는 이번 재검증 범위 밖이다.
- `37.1234564` → `37.123456`, `37.1234565` → `37.123457`, `-37.1234565` → `-37.123457`.
- `90.0000004`는 반올림 후 90이 될 수 있어도 원본이 범위 밖이므로 거절한다.
- 정상 원본 `89.9999999`는 `90.000000`으로 저장할 수 있다.
- 기존 등록 성공 응답은 `201`과 공고·일정 ID 형식을 유지한다. 저장된 좌표는 아래 GET으로 확인한다.

## 공고 조회

기존 권한과 응답 필드를 유지하고 공고 단위에 다음 두 필드를 추가한다.

| 경로 | 좌표 위치 | 역할 |
| --- | --- | --- |
| `GET /api/job-postings/mine` | `jobPostings[].latitude`, `longitude` | 소유 고용주 |
| `GET /api/job-postings` | `jobPostings[].latitude`, `longitude` | 근로자 |
| `GET /api/job-postings/{jobPostingId}` | `latitude`, `longitude` | 근로자 |

응답 추가 필드 예시(전체 응답 아님):

```json
{
  "workLocation": "고용주가 직접 입력한 실제 작업지 주소",
  "latitude": 37.123457,
  "longitude": 127.123457
}
```

기존 좌표 없는 공고는 두 필드 모두 `null`이다. 주소 검색으로 채우거나 공고를 숨기지 않는다. 공고 노출·지원 가능 여부는 APP-01의 기존 기준을 유지한다. 작업지 수정 API는 이번에 추가하지 않았다.

## 보험 확정 근무 상세

`GET /api/internal/insurance/workers/{workerId}/work-assignments/{assignmentId}`의 서버 토큰·근로자·근무 소유권 확인을 유지한다.

추가 필드 예시(전체 응답 아님):

```json
{
  "agreedLatitude": 37.123457,
  "agreedLongitude": 127.123457
}
```

- `work_assignment.agreed_latitude`·`agreed_longitude`만 숫자로 반환한다.
- 양쪽이 없는 기존 약정은 두 필드 모두 `null`로 반환한다. 다른 필수 약정 정보 누락에 대한 기존 503 처리는 유지한다.
- 한쪽만 있는 불완전한 좌표는 기존 `503 SERVICE_UNAVAILABLE`로 처리한다. V7의 DB CHECK도 한쪽만 저장하는 것을 막는다.
- 현재 공고 주소·좌표로 과거 약정을 대체하거나 보완하지 않는다.
- 공고 좌표가 새로 생겨도 과거 약정 좌표는 자동으로 바뀌지 않는다.

## DB와 후속 확정 기능

신규 `V7__add_work_location_coordinates.sql`만 추가한다. V1~V6는 수정하지 않는다.

- `job_posting`: `latitude`, `longitude` 각각 `DECIMAL(9,6) NULL`.
- `work_assignment`: `agreed_latitude`, `agreed_longitude` 각각 `DECIMAL(9,6) NULL`.
- 두 테이블 모두 좌표 쌍의 완전성과 범위 CHECK를 추가한다.
- 기존 행은 새 좌표가 양쪽 모두 NULL이다. 자동 보완 UPDATE는 없다.
- 이번 작업에서 DB 적용·공유 DB 버전 조회·서버 실행은 하지 않았다. 서버 기동 시 Flyway가 V7을 실행하므로 공유 DB 적용 상태와 팀 적용 순서를 확인한다.

선정·확정 API는 아직 없다. 후속 WORK 기능에서 확정 트랜잭션 안에 좌표 누락을 거절하고, 공고의 저장된 주소·좌표를 신규 약정에 함께 복사해야 한다. 기존 공고의 좌표 보완을 위한 위치 수정 API도 후속 범위다. 이번 PR만으로 신규 확정 시 복사가 완료됐다고 해석하지 않는다.

## 검증 범위

사용자 지시에 따라 단위·통합 테스트, 서버·DB 실행은 하지 않는다. 기존 테스트의 요청 생성 데이터·DTO 생성자·응답 필드 목록·최신 마이그레이션 버전 기대값만 새 계약에 맞춘다. 실제 좌표 저장·반올림·기존 데이터 NULL·약정 보존의 실행 검증은 후속 독립 테스트 대상이다.

## 개인용 farm-demo에서 확인

로컬 DB 연결과 V7 적용 상태를 확인하고 기존 farm-demo 설정으로 서버를 다시 실행한다. 기존 주소가 18081이라면 `http://127.0.0.1:18081/demo/login`에서 로그인한 뒤 **작업지 좌표 등록 · 조회 확인**을 누른다. 직접 주소는 `/demo/job-location`이다. 개인 로컬 사용은 `SERVER_ADDRESS=127.0.0.1` 설정을 사용한다.

### 고용주: 저장·반올림·거절

1. 고용주로 로그인한다. 화면의 기본 근무일은 서울 날짜 기준 7일 뒤다.
2. **반올림 예시 넣기**를 누른다. 위도 `37.1234565`, 경도 `127.9876544`가 입력된다.
3. **실제 API로 공고 등록**을 누른다. 공고 등록 POST 직전에 현재 CSRF 토큰을 자동으로 발급받아 전송한다. 토큰은 화면·요청 기록·저장소에 출력하지 않는다.
4. 등록 201과 공고 ID를 표시한 뒤 `/api/job-postings/mine`으로 저장값을 자동 재조회한다. 위도 `37.123457`, 경도 `127.987654`를 원본과 비교한다. 최근 요청에는 등록 201과 조회 200이 각각 남는다.
5. **범위 초과 예시 넣기** 후 등록하면 원본 위도 `90.0000004`를 서버가 400으로 거절하는지 확인한다. 브라우저의 입력 범위 제한으로 요청을 막지 않는다.
6. **좌표 누락 예시 넣기** 후 등록하면 양쪽 null의 필수값 오류를 확인한다. 경도·음수·경계값은 직접 입력할 수 있다.
7. 기존 공고 ID로 **저장값 조회**를 누르면 재조회한다. 기존 좌표 없는 공고는 null로 표시한다. 고용주의 조회는 내 공고 목록 API를 사용하므로 상대 공고는 표시하지 않는다. HTTP가 200이지만 내 목록에서 찾지 못한 경우도 실제 상태와 구분해 안내한다.

각 정상 등록은 실제 공고를 생성한다. 자동 등록·임의 초기화·자동 재시도는 하지 않는다. 등록 성공 후 재조회만 실패하면 성공한 공고 ID를 유지하고 조회 실패를 별도로 안내한다. 네트워크 오류로 등록 결과를 알 수 없으면 먼저 내 공고에서 확인한다.

입력 소수는 JavaScript Number로 변환해 반올림하지 않고 JSON 숫자 원문으로 보낸다. 따라서 `90.0000000000000001`도 전송 전에 90으로 바뀌지 않는다. 저장 좌표의 화면 표시는 6자리이며 실제 응답 원문도 함께 제공한다. 일반 텍스트를 좌표에 넣으면 JSON 문자열로 보내 서버의 형식 오류를 확인한다.

### 근로자: 공고·기존 약정 null

1. 로그인 화면에서 로그아웃하고 근로자로 로그인해 같은 확인 화면으로 이동한다.
2. 등록 때 받은 공고 ID로 **저장값 조회**하면 실제 근로자 공고 상세 API를 호출한다.
3. **내 약정 목록 조회**로 본인 최근 100건만 조회한다. `좌표 없음`으로 표시된 약정을 선택하거나 본인 약정 ID를 직접 입력한다.
4. **약정 응답 조회**를 누르고 실제 200 응답의 `agreedLatitude`, `agreedLongitude`가 양쪽 null인지 확인한다. 상세 서비스가 다른 필수 약정 누락으로 503을 반환하면 해당 오류를 그대로 표시한다.
5. 본인 약정이 없으면 그 사실을 안내한다. 가짜 null 성공 응답이나 테스트용 약정을 자동으로 생성하지 않는다. 100건 밖의 본인 약정은 ID를 직접 입력할 수 있다.

약정 확인은 **farm-demo 전용 세션 API**다.

- `GET /demo/api/work-assignments`: 세션 근로자의 약정 선택 목록.
- `GET /demo/api/work-assignments/{assignmentId}`: 동일한 `WorkAssignmentQueryService`의 실제 약정 응답.
- 두 경로는 farm-demo에서만 등록·허용한다. 현재 DB 역할과 본인 소유 관계를 확인하며 캐시를 금지한다.
- 클라이언트에서 workerId·서버 URL·서버 토큰을 받지 않는다. 보험 서버용 Bearer 토큰을 브라우저에 보내지 않는다.
- 실제 `/api/internal/insurance/**` 인증 체인은 변경하지 않았다. 이 화면으로 보험 HTTP 인증까지 검증했다고 해석하지 않는다.

하단에는 실제 호출 경로·HTTP 상태·오류 코드와 필드·요청 JSON·응답 원문을 표시한다. 세션 계정이 바뀌거나 인증·권한 오류가 나면 이전 결과를 지운다. 회원·작업지·오류 문자열은 HTML로 삽입하지 않고 textContent로 표시한다.

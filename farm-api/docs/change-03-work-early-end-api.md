## 요청 흐름

현재 DB 역할을 다시 확인하고 본인 공고의 개인별 확정 근무만 처리한다. 다른 고용주 소유와 없는 근무는 모두 404다. 근로자 본인 조기 종료, 정정·문의 접수 도구는 이번 범위에 포함하지 않는다.

## 요청

```http
POST /api/work-assignments/7001/early-end
Content-Type: application/json
X-CSRF-TOKEN: {고용주 로그인 후 새로 발급받은 토큰}
Cookie: FARMSESSION={고용주 세션}
```

```json
{
  "actualEndAt": "2026-12-02T14:00:00+09:00",
  "reasonCode": "WEATHER",
  "weatherReasonCode": "RAIN",
  "reasonDetail": "  강수로 작업을 중단했습니다.  "
}
```

| 필드 | 규칙 |
|---|---|
| actualEndAt | 필수. 오프셋 포함 ISO 8601 문자열. 대문자 T, Z 또는 ±HH:mm 오프셋. 소수초 최대 6자리 |
| reasonCode | WEATHER / FARM_CIRCUMSTANCES / OTHER 중 필수 |
| weatherReasonCode | WEATHER이면 RAIN / WIND / HEAT / OTHER 중 필수. 나머지는 생략 또는 null |
| reasonDetail | 선택. 양 끝 공백 제거 후 빈 값은 null. 유니코드 코드 포인트 최대 500개 |

actualEndAt의 예:
- 2026-12-02T14:00:00+09:00
- 2026-12-02T14:00+09:00 (초 생략은 0초)
- 2026-12-02T05:00:00Z
- 2026-12-02T14:00:00.123456+09:00

오프셋 없는 현지 일시·숫자·배열·객체·불리언·유효하지 않은 달력 날짜를 거절한다. 소수초가 7자리 이상이면 뒤가 0이어도 거절하고 자르지 않는다. Z는 UTC 시점으로 해석하며 삭제하지 않는다. 오프셋 초 단위 표기나 지역 ID를 붙인 문자열은 받지 않는다. 전역 Jackson 설정과 기존 API의 형식은 바꾸지 않는다.

사유와 설명은 JSON 문자열만 받는다. 설명의 중간 공백·줄바꿈은 보존하고 길이에 포함한다. 이모지처럼 UTF-16 길이가 2여도 코드 포인트 1개인 문자는 1개로 센다. 500개 초과 설명은 잘라 저장하지 않고 400으로 거절한다.

## 허용 상태와 시간 규칙

신규 기록:
- 취소·조기 종료·완료가 없는 정상 확정 근무만 허용한다.
- 서버 현재 시각이 약정 시작 시각 이상이어야 한다. 시작 시각과 같은 시각부터 허용한다.
- 실제 종료 시각은 약정 시작 이상·약정 종료 미만이며 서버 현재 시각보다 미래일 수 없다.
- 최초 기록은 약정 종료 시각 + 24시간까지 포함해 허용한다.
- 기한을 넘기면 409와 문의 안내를 반환한다. 정상 완료나 다른 사유로 자동 변경하지 않는다.
- 현재 공고가 아닌 저장된 agreedStartAt·agreedEndAt·agreedTimeZone으로 계산한다.
- 약정 시각·시간대가 없거나 모호하거나 종료가 시작보다 늦지 않으면 추측하지 않고 503이다.
- 모집 중·일시중단·마감 상태 때문에 개인별 조기 종료를 차단하지 않는다.

예: 약정 12월 2일 09:00~17:00이면 최초 기록은 12월 3일 17:00까지다. 실제 종료는 09:00 이상·17:00 미만이어야 한다. 요청을 18시에 보내도 실제 종료를 14시로 기록할 수 있다.

잠금 대기가 끝난 서버 시각으로 판단한다. 경계 비교 전에 현재 시각을 마이크로초로 잘라 미래나 기한 경계를 느슨하게 만들지 않는다. 저장 시각만 DB의 마이크로초 정밀도로 낮춘다.

## 동일 재요청과 충돌

역할·소유권·현재 완료/변경 기록을 확인한 뒤 신규 시간 규칙을 적용한다.

- 기존 EARLY_ENDED의 실제 종료 시점·사유·기상 세부 사유·정규화한 설명이 같으면 200이다.
- 시간 문자열이 달라도 같은 Instant이면 같은 종료 시점이다. 예를 들어 14:00+09:00과 05:00Z는 동일하다.
- 입력 기한 이후에도 동일 요청은 기존 결과를 반환한다. 현재 시각·약정 시작/종료 범위로 재거절하지 않는다.
- 다른 내용은 409 EARLY_END_CONTENT_CONFLICT다. 이전 기록을 수정하지 않는다.
- 동일 요청에서는 변경 ID·sourceVersion·effectiveAt·recordedAt·updatedAt·보험 발행 순번을 갱신하지 않는다.
- 기존 취소는 WORK_ALREADY_CANCELLED, 기존 완료는 WORK_ALREADY_COMPLETED로 거절한다.
- 같은 내용 비교는 현재 저장된 변경 기록을 기준으로 한다. 후속 사유 보완 후 이전 내용을 재전송해 덮어쓰지 않는다.

## 성공 응답

최초 기록과 같은 내용 재요청은 모두 200 OK와 Cache-Control: no-store다.

```json
{
  "assignmentId": 7001,
  "changeId": 9002,
  "changeType": "EARLY_ENDED",
  "reasonCode": "WEATHER",
  "weatherReasonCode": "RAIN",
  "reasonDetail": "강수로 작업을 중단했습니다.",
  "effectiveAt": "2026-12-02T14:00:00+09:00",
  "recordedAt": "2026-12-02T18:00:00+09:00",
  "updatedAt": "2026-12-02T18:00:00+09:00",
  "sourceVersion": "1"
}
```

effectiveAt은 실제 종료 시각이고, recordedAt은 최초 저장 시각이다. DB에는 UTC·마이크로초로 저장하고 응답은 약정 시간대의 오프셋으로 변환한다. GMT+9이면 +09:00이다.

## 오류 응답

```json
{
  "code": "EARLY_END_DEADLINE_PASSED",
  "message": "조기 종료를 직접 기록할 수 있는 시간이 지났습니다. 실제 조기 종료 사실의 확인이 필요하면 담당자에게 문의해 주세요."
}
```

| HTTP | 코드 | 조건 |
|---|---|---|
| 400 | INVALID_REQUEST | ID·본문·사유·설명 오류, 실제 종료 시각이 약정 범위 밖이거나 미래 |
| 401 | 기존 인증 응답 | 로그인 없음 |
| 403 | EMPLOYER_ROLE_REQUIRED | 근로자 또는 현재 DB 역할이 고용주가 아님 |
| 403 | 기존 CSRF 오류 | CSRF 누락·오류 |
| 404 | WORK_ASSIGNMENT_NOT_FOUND | 근무 없음 또는 다른 고용주 소유 |
| 409 | WORK_NOT_STARTED | 신규 요청인데 약정 시작 전 |
| 409 | WORK_ALREADY_CANCELLED | 기존 취소 기록 있음 |
| 409 | WORK_ALREADY_COMPLETED | 기존 완료 기록 있음 |
| 409 | EARLY_END_CONTENT_CONFLICT | 기존 조기 종료와 실제 종료 시점·사유·설명이 다름 |
| 409 | EARLY_END_DEADLINE_PASSED | 최초 기록이 약정 종료 + 24시간을 초과 |
| 409 | WORK_STATE_CONFLICT | DB 무결성 충돌 |
| 415 | INVALID_REQUEST | 지원하지 않는 본문 Content-Type |
| 503 | SERVICE_UNAVAILABLE | 약정 해석 불가·DB 장애·잠금 시간 초과 등 |
| 500 | INTERNAL_SERVER_ERROR | 기타 내부 오류 |

입력 형식 검증 후 기존 완료·취소·조기 종료를 확인한다. 신규 요청은 시작 여부 → 입력 기한 → 실제 종료 범위 순으로 검사한다. 성공·컨트롤러 오류 응답은 no-store이며 인증·CSRF 오류는 기존 보안 체인을 유지한다. 입력 원문·SQL 예외·개인정보를 오류 메시지에 포함하지 않는다.

## 저장과 보험 주기 조회

WorkChangeRecorder.endWork는 근로자 보험 변경 스트림 → 확정 근무 → 변경 행 순서로 잠근다. 변경 원본·발행 순번·불변 버전을 같은 READ_COMMITTED 트랜잭션으로 저장한다. WorkEarlyEndService의 응답 구성도 같은 트랜잭션에서 처리한다. 실제 MySQL 경합·롤백은 실행 검증하지 않았다.

- 기존 지원 상태를 미선정으로 바꾸거나 약정을 삭제하지 않는다.
- 같은 날짜의 다른 근로자나 날짜 모집 상태를 변경하지 않는다.
- 종료된 자리로 정원을 자동 복원하거나 모집을 재개하지 않는다.
- 보험 주기 조회에는 EARLY_ENDED와 실제 종료 시각을 제공한다.
- 기상·농장 사정·기타를 모두 기록한다. 위험 지수와 보험 심사·지급 여부는 농업 서버가 판정하지 않는다.
- 문의 창구와 예외 정정 절차는 후속 합의 대상이다. 기한 초과 안내까지만 제공한다.

기존 recordValidatedChange·reviseReason과 취소/완료 기반 코드는 유지한다. 기존 저장 경계의 내부 시연 호출을 새 사용자 API와 혼동하지 않는다.

## farm-demo 시연 데이터 준비

```http
POST /demo/api/work-early-end/fixtures
X-CSRF-TOKEN: {고용주 로그인 후 새로 발급받은 토큰}
Cookie: FARMSESSION={고용주 세션}
```

farm-demo 전용이고 고용주 세션·현재 DB 역할·CSRF를 요구한다. 별도 가상 공고와 demo-worker의 확정 근무를 준비하므로 앞선 지원·선정을 수동 반복할 필요가 없다. demo-worker 계정은 미리 있어야 한다. 새 공고는 201, 재사용은 200이다. 간이 화면 `/demo/work-early-end`에서 준비 버튼으로 호출할 수 있다.

| scenario | 확인 내용 |
|---|---|
| NORMAL | 최초 기록 200 → 동일 200 → 다른 내용 409 |
| LATE_ALLOWED | 약정 종료 후 24시간 안의 늦은 최초 기록 |
| NOT_STARTED | 시작 전 409 |
| DEADLINE_PASSED | 기한 초과 409와 문의 안내 |
| CANCELLED | 취소 근무 거절 409 |
| EARLY_ENDED | 기존 조기 종료의 기한 이후 동일 재요청 200 |
| COMPLETED | 완료 근무 거절 409 |

응답의 assignmentId와 suggestedRequest를 정식 early-end API에 사용한다. agreedStartAt·agreedEndAt·recordingDeadline도 제공한다. 정상·늦은 입력 사례는 당일 언제든 확인하도록 00:00~23:59:59.999999 가상 약정을 사용한다.

- 날짜 기준은 요청 안에서 한 번 정하고 공고 표식·생성·응답에 재사용한다.
- 응답 조회는 생성/재사용한 공고 ID·소유자·근로자·표식으로 제한한다.
- 사례 종류는 근무일과 기준 날짜의 매핑으로 정한다. DB 정렬 인덱스로 잘못 분류하지 않는다.
- 기존 기록 재요청 사례는 내부 저장 경계로 준비한 가상 과거 기록이다. 신규 사용자 API의 최초 입력 기한을 느슨하게 만들지 않는다.
- 반복 준비로 이미 조기 종료·취소·완료된 상태를 초기화하지 않는다.
- 선택한 worker의 요청 잠금을 사용해 같은 날 병렬 준비가 중복 공고를 만들지 않도록 구성했다.
- 실제 계정의 이름·비밀번호와 실제 공고·약정은 수정하지 않는다.
- 원래 wonday의 .env를 자동 복사하거나 키를 출력하지 않는다. 실행 시 기존 환경 설정을 별도로 연결해야 한다.

5. 달력·시간과 실제 전송 시각에는 서버가 준 suggestedRequest.actualEndAt이 채워진다. 먼저 기본값으로 진행한다.
6. 사유 기상·세부 사유 강수를 확인하고 「조기 종료 기록 보내기」를 누른다.
7. 「4. 최근 조기 종료 API 응답」에 HTTP 200이 표시되는지 확인한다.
8. 변경 ID·버전·실제 종료 일시·최초 저장 일시·최종 수정 일시를 확인한다.
9. 표와 별도 DB 재조회가 「조기 종료」로 바뀌는지 확인한다.

정상 사례가 이미 조기 종료되어 있으면 첫 요청도 기존 결과 200이다. 같은 날 다시 준비해 초기화하지 않는다. 최초 기록을 추가 확인하려면 아직 정상 확정인 「약정 종료 후 24시간 이내 늦은 입력」 사례를 선택할 수 있다.

### 동일 재요청 200

1. 같은 사례에서 기록 200을 받은 뒤 「같은 내용으로 재요청 · 200 확인」을 누른다.
2. HTTP 200과 「기존 결과 유지 확인」 문구를 확인한다.
3. 변경 ID·사유·버전·실제 종료/저장/수정 시각이 유지되는지 확인한다.

버튼은 직전 성공 요청 본문을 그대로 복사한다. 달력·시간·사유 입력 칸을 바꿔도 재요청 본문을 바꾸지 않는다. 기존 조기 종료 사례를 선택하면 실제 저장된 종료 시각과 사유를 기본값으로 채운다.

### 다른 내용 409

1. 기록 200을 받은 상태에서 「다른 사유로 재요청 · 409 확인」을 누른다.
2. HTTP 409와 EARLY_END_CONTENT_CONFLICT를 확인한다.
3. 「종료 시각 변경 · 409 확인」도 눌러 같은 오류 코드를 확인한다. 이 버튼은 직전 성공 시각에 정확히 1초를 더하고 소수초는 유지한다.
4. 이전 성공의 변경 ID·버전·세 시각이 화면에 남는지 확인한다.
5. 다시 「같은 내용으로 재요청 · 200 확인」을 누르면 원래 성공 요청으로 200을 받을 수 있다.

다른 내용 요청은 마지막 성공 요청과 비교 기준을 덮어쓰지 않는다. 전송한 본문과 응답은 각각 접힌 원문 항목에서 확인할 수 있다.

### 입력 기한 초과와 문의 안내

1. 사례 표에서 「입력 기한 초과 409·문의 안내」 행을 찾는다.
2. 그 행 오른쪽 「이 사례 선택」을 누른다.
3. 선택한 확정 근무 ID와 이미 지난 「직접 입력 마감」을 확인한다.
4. 기본 종료 시각·사유를 유지하고 「조기 종료 기록 보내기」를 누른다.
5. HTTP 409, EARLY_END_DEADLINE_PASSED와 담당자 문의 안내를 확인한다.
6. 별도 DB 재조회에서 해당 근무가 정상 확정으로 남고 완료 일시는 없는지 확인한다. 기한 경과를 정상 완료로 바꾸지 않는다.

입력 기한이 지난 동일 재요청은 「기존 조기 종료·기한 이후 동일 재요청」 사례를 선택해 기본값 그대로 보내 확인한다. 이 경우에는 200이다.

### 추가 확인과 표시 원칙

- 「시작 전 409」: WORK_NOT_STARTED.
- 「취소 근무 거절 409」: WORK_ALREADY_CANCELLED.
- 「완료 근무 거절 409」: WORK_ALREADY_COMPLETED.
- 설명 501 코드 포인트·기상 세부 사유 누락: 400 INVALID_REQUEST.
- 실제 종료 일시는 datetime-local로 선택하고 +09:00 오프셋을 자동으로 붙인다. 입력 범위를 브라우저에서 막아 서버 검증을 가리지 않는다.
- 서버의 기본 시각은 소수초 최대 6자리를 별도로 보존한다. 브라우저 Date에는 소수초를 제거한 초 부분만 전달하고, 시간대 변환 후 원래 소수초를 붙인다.
- 일부 브라우저가 긴 소수초를 달력에 표시하지 못하더라도 「실제 전송 시각」은 원본을 유지한다. 사용자가 달력·시간을 편집하면 해당 입력값으로 전송 시각을 갱신한다.
- POST마다 새 CSRF를 받아 헤더에 넣는다. 토큰·세션 쿠키·보험 서버 토큰을 화면이나 웹 저장소에 기록하지 않는다.
- 중복 클릭과 자동 POST 재시도는 하지 않는다. POST 응답과 보조 GET 응답은 별도로 표시한다.
- 보조 GET이 실패해도 기록 응답·선택·재요청 정보를 지우지 않는다.
- 요청 전후 /me로 계정과 역할을 확인한다. 계정이 바뀌면 이전 사례·응답을 지우고 다시 준비하도록 한다.
- pagehide 뒤 도착하는 응답은 무효화한다. 사용자 문자열은 textContent로 표시한다.


## 검증 범위

사용자 요청에 따라 테스트·Spring 서버·실제 DB·이관·커밋·푸시는 실행하지 않는다. 운영 코드 컴파일과 diff 확인만 수행한다. HTTP·CSRF·실제 Security 체인·MySQL 조회/잠금·트랜잭션 롤백·보험 상호 호출은 후속 검증 대상이다. 기존 선정·취소 테스트 결과를 조기 종료 API의 검증 결과로 합산하지 않는다.

운영 코드 `compileJava --offline --no-daemon --console=plain`은 성공했고 `git diff --check`도 통과했다. 테스트 태스크는 실행하지 않았다.

# 보험 서버용 농업 플랫폼 연동 API

이 문서는 팀에서 전달한 API 초안을 구현한 현재 범위와 후속 기능에서 연결할 지점을 설명한다.

## 역할과 호출 순서

1. 보험 서버가 이름·전화번호·가상 주민번호로 농업 근로자를 확인한다.
2. 응답의 `workerId`를 보험 회원과 연결한다. 농업 회원 ID를 그대로 사용한다.
3. 보험 서버가 연결된 근로자의 변경 목록을 커서로 주기 조회한다.
4. 변경의 `assignmentId`로 확정 당시 약정 상세를 조회한다.

보험 상품 가입은 상품 단위다. 근무 상세와 변경 기록은 이후 계약·개인별 확정 근무의 심사를 위해 사용한다. 기상 판정·보험금 계산·중복 접수 처리는 보험 서버가 담당한다.

## 현재 제공하는 경로

| 메서드 | 경로 | 역할 |
| --- | --- | --- |
| POST | `/api/internal/insurance/worker-verifications` | 근로자 본인 확인 |
| GET | `/api/internal/insurance/workers/{workerId}/work-changes` | 개인별 취소·조기 종료의 불변 버전 목록 |
| GET | `/api/internal/insurance/workers/{workerId}/work-assignments/{assignmentId}` | 본인 확정 근무의 약정 상세 |

세 경로는 `Authorization: Bearer {token}`으로 호출한다. 농업 앱의 로그인·쿠키·CSRF 토큰을 사용하지 않는다. 기존 농업 앱 API는 기존 세션·CSRF 보호를 유지한다. 내부 API 응답에는 `Cache-Control: no-store`를 붙인다.

## 설정과 동의 확인 책임

농업 서버와 보험 서버에 같은 `FARM_API_SERVICE_TOKEN`을 설정한다. 보험 서버는 기존 `FARM_API_BASE_URL`을 농업 서버 주소로 지정한다. 현재처럼 농업 서버를 18081 포트로 실행하면 `http://127.0.0.1:18081`을 사용한다. 토큰 값은 코드·PR·브라우저에 넣지 않는다.

**2026-11-24 팀 합의:** 보험 서버가 동의를 관리하고 농업 서버는 서버 전용 Bearer 토큰으로 호출 서버를 인증한다.

- 보험 서버는 매 조회 전에 유효한 동의·철회 여부와 연결된 근로자를 확인한다. 동의가 철회되면 해당 근로자의 조회를 중단한다.
- 농업 서버는 별도 동의 테이블이나 보험 로그인 세션을 조회하지 않는다. 토큰 검증 후 근로자 존재·역할과 요청 근무의 소유 관계를 확인한다.
- 이전 임시 설정 `FARM_INSURANCE_CONSENT_MODE`는 제거했다. 동의 대기로 인한 403 차단은 없다.
- 서버 토큰은 개별 근로자의 동의를 증명하지 않는다. 보험 서버가 동의·연결 범위를 지켜 호출한다는 역할 분담이다.

## 본인 확인

```json
{
  "name": "데모 근로자",
  "phone": "010-0000-0000",
  "residentRegistrationNumber": "000000-0000000"
}
```

이름은 앞뒤 공백을 제거한다. 전화번호·가상 주민번호는 하이픈·공백 제거 후 각각 ASCII 숫자 10~11자리, 13자리인지 확인한다. JSON 값은 문자열이어야 한다. DB의 기존 저장값에도 정규화를 적용하고 세 값이 모두 일치하는 `WORKER`만 두 건까지 조회한다.

- 한 명: `200`과 `workerId`, 정규화된 이름·전화번호
- 없음 또는 고용주만 일치: `404 WORKER_IDENTITY_NOT_MATCHED`
- 두 명 이상: `409 WORKER_IDENTITY_AMBIGUOUS`
- 필수값·형식 오류: `400 INVALID_REQUEST`

주민번호나 항목별 대조 결과는 응답하지 않는다. 입력 DTO의 `toString()`에도 개인정보를 출력하지 않는다. 회원가입 API는 추가하지 않는다.

현재 기본 데모 근로자는 전화번호·가상 주민번호가 비어 있다. **본인 로컬 개발 DB에서만**, 시연 계정에 다음과 같이 가상 정보를 넣을 수 있다. 이 문서의 SQL은 자동 실행되지 않는다.

```sql
USE farm_db;
UPDATE member
SET phone = '01000000000', resident_registration_number = '0000000000000'
WHERE login_id = 'demo-worker' AND role = 'WORKER';
```

## 확정 당시 조건과 시각

`work_assignment`에 저장된 약정만 반환한다. 현재 공고에서 시간대·작업지·일급 등을 가져와 보완하지 않는다. 다른 근로자의 근무는 `404 WORK_ASSIGNMENT_NOT_FOUND`다. 휴게가 없으면 두 필드 모두 `null`이다.

**2026-11-26 좌표 응답 추가:** `agreedLatitude`·`agreedLongitude`는 V7에서 추가한 약정 좌표를 JSON 숫자로 반환한다. 좌표 없는 기존 약정은 두 필드 모두 `null`이고, 한쪽만 있으면 `503 SERVICE_UNAVAILABLE`이다. 현재 공고에서 좌표를 가져와 채우지 않는다. 신규 공고의 좌표 저장·범위·반올림과 후속 확정 연결은 [좌표 API 문서](job-location-api.md)를 참고한다. 다른 필수 약정 누락에 대한 기존 오류 처리는 유지한다.

- `agreedWorkDate`: 약정 현지 날짜
- `agreedTimeZone`: 확정 당시 저장된 시간대 원문
- 약정 근무·휴게 시각: 저장된 현지 일시에 약정 시간대의 오프셋 부여
- `confirmedAt`: 새 `confirmed_at_utc`를 약정 시간대의 오프셋으로 표현

시간대는 기존 합의대로 `GMT+9`를 유지하고 API의 시각은 `+09:00`으로 반환한다. 팀 초안의 `Asia/Seoul` 예시로 저장 정책을 바꾸지 않는다 (2026-11-24 사용자 확인). 기존 약정이 있다면 저장된 원문을 임의로 다시 쓰지 않는다. 코드 목록 역시 새로 정의하지 않고 약정에 보관된 실제 코드를 반환한다.

기존 `confirmed_at`에는 시간대가 없으므로 UTC였는지 한국 시각이었는지 추측하지 않는다. V5는 `confirmed_at_utc`, `agreed_work_date`, `agreed_time_zone`을 NULL 허용으로 추가하며 기존 행을 자동 보완하지 않는다. 필수 약정이 누락된 기존 근무의 상세는 `503 SERVICE_UNAVAILABLE`로 반환한다. 보완은 원본을 확인한 별도 작업이다.

## 변경 버전과 커서

호출 예시:

```http
GET /api/internal/insurance/workers/123/work-changes?limit=100
Authorization: Bearer {token}
```

`cursor`가 없으면 처음부터 읽는다. `limit` 기본값은 100, 범위는 1~500이다. 응답의 `nextCursor`를 다음 요청에 그대로 사용한다. 빈 배열에도 커서를 반환하며, 같은 근로자의 같은 조회 위치는 같은 커서를 재사용한다. 다른 근로자의 커서·변조된 커서는 `400 INVALID_CURSOR`다.

- `work_change`: 개인별 현재 변경 상태와 고정된 최초 시각
- `work_change_version`: 각 버전의 불변 응답 데이터
- `insurance_change_stream`: 근로자별 발행 순서와 잠금
- `insurance_change_cursor`: 근로자와 조회 위치에 연결된 불투명 UUID

농장 사정·조기 종료·전날 취소도 모두 제공한다. 보험 심사에서 제외할지 판단하는 것은 보험 서버의 역할이다.

변경 최초 저장·사유 보완·폴링은 **같은 근로자 스트림 행을 잠근다.** 순번 증가와 버전 저장을 한 트랜잭션으로 커밋한다. 단순한 AUTO_INCREMENT ID나 `updated_at`만 커서로 쓰지 않으므로 먼저 ID를 배정받고 늦게 커밋되는 기록이 건너뛰어지는 것을 방지하도록 구성했다. 실제 MySQL에서의 동작은 통합 검증 대상이다.

최초 변경은 `sourceVersion: "1"`이다. 사유 보완은 새 버전을 추가하며 `changeId`, `effectiveAt`, `recordedAt`을 유지한다. 이전 버전은 덮어쓰지 않아 같은 `changeId + sourceVersion`의 응답 내용을 보존한다. 보험 서버는 수신 기록과 커서를 함께 저장하고 같은 키로 중복을 방지한다.

## 후속 농업 기능에서 연결할 부분

이번 구현이 선정·취소·조기 종료 화면과 사용자 API까지 완성한 것은 아니다.

- WORK-04의 확정 저장 시 날짜·시간대·약정 조건과 정확한 UTC 확정 시각을 함께 기록해야 한다.
- 신규 확정은 공고의 좌표 누락을 먼저 거절하고, 저장된 주소·위도·경도를 약정에 함께 복사해야 한다. 확정 생성 API 자체는 아직 구현하지 않았다.
- CHANGE 기능은 실제 시작 여부와 취소/조기 종료 가능 여부를 검증한 후 `WorkChangeRecorder.recordValidatedChange`를 호출한다.
- 사유 보완은 `WorkChangeRecorder.reviseReason`을 사용한다.
- 최초 취소 발생 시각은 서버가 부여한다. 조기 종료 발생 시각은 검증된 실제 종료 시각이다.
- 근무 상태 변경과 버전 저장은 같은 트랜잭션으로 연결하고, 저장·폴링의 스트림 잠금 규칙을 지켜야 한다. 여러 근로자를 한 트랜잭션으로 처리할 때는 근로자 ID 오름차순으로 잠근다.
- 변경 행만 직접 INSERT/UPDATE하면 폴링 버전이 생성되지 않는다. 후속 기능에서 이 저장 경계를 우회하지 않는다.
- RabbitMQ, 취소 푸시 통지, EVENT_OUTBOX는 추가하지 않았다.

변경이 없으면 실제로 빈 목록을 반환한다. 확정 근무나 변경 내역을 임의로 생성하지 않는다. 실제 데이터 흐름 전체 시연은 해당 원본 생성 기능 또는 별도의 격리된 가상 데이터 준비 후 가능하다.

## 적용과 검증 범위

기존 적용 마이그레이션 V1~V4는 수정하지 않았으며 새 V5만 추가했다. 이 작업에서는 DB에 적용하지 않았다. 다음 서버 시작 시 Flyway가 V5를 실행하므로 공유 DB에서는 팀과 버전 충돌·적용 순서를 확인한 뒤 실행한다.

단위·통합 테스트, API 요청, 실제 DB 마이그레이션은 실행하지 않았다. 컴파일 결과는 작업 완료 안내를 기준으로 확인한다. 실제 MySQL 정규화·projection·잠금·커밋 역전·롤백·빈 페이지 이후 신규 기록과 두 Security 체인의 분리는 별도 검증해야 한다. 동의·철회 처리는 보험 서버의 검증 범위다. 기존 226개 통과·JaCoCo 수치는 이 새 기능의 검증 결과가 아니다.

## 팀원에게 전달할 항목

| 항목 | 전달 내용과 현재 상태 |
| --- | --- |
| 코드 | `insurance-integration` 브랜치의 코드. 아직 커밋·푸시하지 않았으므로 현재 원격에서 받을 수 없음 |
| 규격 | 이 문서와 제공한 세 경로의 요청·응답·실패 코드 |
| 접속 주소 | 보험 서버에서 실제로 접근할 농업 서버 주소를 정한 뒤 `FARM_API_BASE_URL`로 전달. 서로 다른 PC라면 `127.0.0.1`은 공유 접속 주소가 아님 |
| 인증 | 양 서버의 `FARM_API_SERVICE_TOKEN` 값을 맞춤. 실제 값은 저장소·PR 본문에 올리지 않고 별도 전달 |
| 동의 | 보험 서버가 유효성·철회·연결 대상 근로자를 확인 |
| 시간대 | `agreedTimeZone: "GMT+9"`, 시각은 `+09:00` 포함 |
| 시연 계정 | 가상 이름·전화번호·주민번호와 실제 본인 확인 응답의 `workerId`. 아직 DB에 준비하거나 확인하지 않음 |
| 시연 근무 | 실제 `assignmentId`, 당일·전날 취소, 농장 사정, 조기 종료, 사유 보완 및 다중 페이지 데이터. 원본 기능 또는 격리된 가상 데이터 준비 필요 |
| 공통 코드 | 작목·작업 유형 코드 목록은 아직 팀 합의 필요. `CABBAGE`, `HARVEST`를 확정 목록으로 취급하지 않음 |
| DB | 새 V5 파일과 적용 순서 공유. 실제 DB에는 아직 적용하지 않음 |
| 검증 | 컴파일과 테스트 결과를 구분해 전달. 이번 새 API의 단위·통합·상호 호출 검증은 아직 미실행 |

검증 후 코드를 커밋·푸시하고 PR 또는 커밋 링크를 전달해야 팀원이 같은 구현을 받을 수 있다. 실제로 접속 가능한 주소·토큰·가상 데이터가 준비된 뒤 양 서버의 상호 호출을 확인한다.

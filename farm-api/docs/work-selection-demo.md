## 처리 파일 흐름

### 실제 선정

farm-work-selection.html → 기존 SecurityConfig → WorkSelectionApi → WorkSelectionService →
JobPostingRepository/WorkScheduleRepository/JobApplicationRepository의 잠금 →
ApplicationConditionAcknowledgementRepository 확인 →
WorkSelectionRepository 저장 → WorkSelectionResponse.

정원 검사·지원 SELECTED 변경·약정 복사를 한 트랜잭션으로 구성한다.
중복 요청은 기존 assignment를 읽어 최초 확정 시각·약정을 유지한다.
새 선정 201, 정상 재요청 200, 취소 근무 409, 조기 종료·완료 재요청 200.

### 실제 재확인

farm-work-selection.html → 기존 SecurityConfig → ConditionConfirmationApi →
ConditionConfirmationService → 공고·일정·지원 잠금 →
ApplicationConditionAcknowledgementRepository → ConditionConfirmationResponse.

최초 지원 버전·시각은 유지한다. 재확인만 지원 ID·버전별 최초 기록으로 보관한다.
같은 최신 버전은 기존 ID·시각으로 200, 최초 지원이 최신이면 별도 재확인 행 없이 200이다.

### 시연 준비

DemoWorkSelectionApi → DemoWorkSelectionFixtureService → JPA 저장소.
준비 POST는 farm-demo의 로그인 세션·CSRF를 사용하며, 고용주/근로자 본인 사례만 조회한다.
정상 선정·재확인 버튼은 demo 대체 API가 아니라 위 실제 API를 직접 호출한다.

기존 회원의 비밀번호·식별정보·업무 이력은 바꾸지 않는다.

## 직접 확인 — 버튼 위치부터

2. /demo/login에서 demo-employer로 로그인한다.

6. 표 오른쪽 버튼이 안 보이면 표 아래 가로 스크롤을 오른쪽으로 움직인다.

### 2. 정상 선정과 재요청

1. 사례 표에서 「정상 선정·같은 선정 재요청」 행을 찾는다.
2. 같은 행 오른쪽 「이 사례 선택」을 누른다.
3. 아래 「2. 선택한 지원의 조건 확인」에서 버전과 근무시간을 읽는다.
4. 「3. 고용주」 영역의 「이 지원자 선정」을 누른다.
5. 「4. 최근 쓰기 결과」에서 HTTP 201과 확정 근무 ID·확정 일시를 확인한다.
6. 「같은 선정 요청 다시 보내기」를 누른다.
7. HTTP 200이며 확정 근무 ID·시각이 처음과 같은지 확인한다.
8. 기존에 이미 선정한 사례를 재사용했다면 첫 요청부터 200인 것이 정상이다.

### 3. 근로자 재확인 전 선정 거부

1. 위 사례 표로 돌아간다.
2. 「변경 조건 재확인 후 선정」 행의 「이 사례 선택」을 누른다.

4. 「이 지원자 선정」을 누른다.
5. HTTP 409 · CONDITION_RECONFIRMATION_REQUIRED를 확인한다.
6. 공고 ID·일정 ID·지원 ID를 기억해 두면 계정 전환 후 같은 사례를 찾기 쉽다.

### 4. 근로자의 재확인과 재요청

1. 화면 위 「로그인 · 계정 전환」으로 이동한다.

5. 같은 공고의 「변경 조건 재확인 후 선정」 행에서 「이 사례 선택」을 누른다.
6. 비교표의 변경 내용을 읽는다.
7. 「3. 근로자」 영역의 「최신 조건으로 지원 유지 · 재확인」을 누른다.
8. HTTP 200과 RECONFIRMATION, 재확인 ID·최초 재확인 일시를 확인한다.
9. 「같은 재확인 요청 다시 보내기」를 누른다.
10. HTTP 200이며 재확인 ID·최초 시각이 같은지 확인한다.
11. 「최신 조건 · 확인 상태 조회」를 누르면 확인 완료 표시가 반영된다.
12. 이미 선정된 뒤에는 재확인 대상이 아니므로 409다.

### 5. 재확인 후 선정

1. 다시 demo-employer로 로그인해 선정 확인 화면으로 돌아간다.
2. 「내 시연 사례 새로 불러오기」를 누른다.
3. 같은 「변경 조건 재확인 후 선정」 사례를 선택한다.
4. 최신 조건 재확인 완료 표시를 확인한다.
5. 「이 지원자 선정」을 누른다.
6. 처음 확정이면 201, 이미 확정했으면 200인지 확인한다.

### 6. 이전 버전 409

1. 고용주로 아직 선정하지 않은 「이전 버전 요청 409」 사례를 선택한다.
2. 조회 버전이 2인지 확인한다.
3. 「이전 버전으로 선정 요청 · 409 확인」을 누른다.
4. HTTP 409 · TERMS_VERSION_CONFLICT를 확인한다.
5. 근로자로 같은 사례를 선택하고 「이전 버전으로 재확인 · 409 확인」을 눌러 같은 오류를 확인한다.
6. 이 버튼은 조회 버전보다 1 작은 값을 의도적으로 전송한다.
7. 일반 요청은 화면에서 본 버전을 자동 사용한다. 다른 창에서 조건을 수정한 경우 「최신 조건 · 확인 상태 조회」 전에는 이전 버전이 유지되어 충돌을 확인할 수 있다.
8. 충돌 후 최신 조건을 직접 조회하고 다시 요청한다. 자동 재시도는 하지 않는다.

### 7. 그 밖의 선정 상태

고용주로 아래 행의 「이 사례 선택」 → 「이 지원자 선정」을 누른다.

| 사례 | 기대 결과 |
| --- | --- |
| 일시중단 상태 선정 | 신규 201, 재요청 200 |
| 마감 상태 | 409 SELECTION_NOT_ALLOWED |
| 모집 취소 상태 | 409 SELECTION_NOT_ALLOWED |
| 시작 시각 경과 | 409 WORK_ALREADY_STARTED |
| 취소된 확정 근무 | 409 WORK_ASSIGNMENT_CANCELLED |
| 조기 종료 근무 재요청 | 200, EARLY_ENDED |
| 완료 근무 재요청 | 200, COMPLETED, 완료 일시 유지 |
| 정원 충족 | 409 CAPACITY_FULL |

### 8. 최초 지원으로 이미 확인된 경우

근로자로 아직 선정하지 않은 「이전 버전 요청 409」 사례를 선택한다.
이 사례는 지원 버전과 최신 버전이 모두 2다.
일반 「최신 조건으로 지원 유지 · 재확인」을 누르면 200, INITIAL_APPLICATION,
재확인 ID·재확인 일시 null이어야 한다. 별도 재확인 행을 만들지 않는다.

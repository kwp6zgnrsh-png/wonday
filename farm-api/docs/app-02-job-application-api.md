# APP-02 여러 날짜 지원 API

## 경로와 인증

`POST /api/job-postings/{jobPostingId}/applications`

농업 근로자 세션(FARMSESSION)과 기존 CSRF를 사용한다. 요청의 근로자 ID는 받지 않고, DB 역할도 재확인한다. 보험 서버 전용 Bearer 토큰은 농업 로그인·CSRF를 대신하지 않는다.

헤더:
```http
Content-Type: application/json
Idempotency-Key: 7c3f6d9a-8e21-4b5f-9a02-61d3e4f50728
X-CSRF-TOKEN: 발급받은_토큰
```

```json
{
  "schedules": [
    { "workScheduleId": 201, "termsVersion": 1 },
    { "workScheduleId": 202, "termsVersion": 3 }
  ]
}
```

- 일정은 1~100개이고, null·중복 ID·0 이하 ID/버전은 400이다.
- ID와 버전은 JSON 정수만 허용한다. 문자열·소수·범위 초과의 자동 변환을 막는다.
- UUID v4 헤더는 정확히 한 개다. 대문자/소문자 UUID는 같은 키로 정규화한다.
- 선택 순서는 의미가 없으며 일정 ID 오름차순으로 정규화해 잠금·응답·요청 비교에 사용한다.
- 공고 ID와 일정 ID·버전 쌍을 정규화한 SHA-256 값으로 같은 요청인지 비교한다. 근로자 ID와 키를 함께 조회하므로 타인의 키로 결과를 읽지 못한다.

## 성공과 재요청

최초 성공은 201이다. 다음은 응답 예시이며 실행 결과가 아니다.

```json
{
  "jobPostingId": 101,
  "applications": [
    {
      "applicationId": 501,
      "workScheduleId": 201,
      "applicationRound": 1,
      "status": "PENDING",
      "appliedTermsVersion": 1,
      "appliedAt": "2026-11-27T15:00:00+09:00"
    },
    {
      "applicationId": 502,
      "workScheduleId": 202,
      "applicationRound": 1,
      "status": "PENDING",
      "appliedTermsVersion": 3,
      "appliedAt": "2026-11-27T15:00:00+09:00"
    }
  ]
}
```

같은 근로자의 같은 성공 키·같은 내용은 200과 최초 본문을 반환한다. 보관 JSON의 일시 오프셋이 읽기·쓰기 문맥 시간대로 바뀌지 않도록 전용 코덱과 응답 필드 설정을 적용한다. ID·회차·접수 시각을 다시 만들지 않는다. 현재 모집 상태나 버전이 바뀌었거나 선정·취소됐어도 최초 접수 결과다. 현재 상태 조회는 후속 APP-04 범위다.

같은 성공 키에 공고·날짜·버전이 다른 요청을 보내면 409다. 성공 결과만 DB에 보관하며 자동 만료·삭제 작업은 없다. 실패 후 내용을 바꾸면 새 키를 사용한다. 실패 키 자체를 별도로 저장하지 않으므로 실패한 키의 사용 이력 전체를 강제하는 기능은 아니다.

## 신규 접수 검증

전체 날짜를 검증한 뒤 날짜별 PENDING 지원을 같은 트랜잭션으로 저장한다.

- 모든 일정이 경로의 공고에 속해야 한다.
- 화면에서 확인한 termsVersion이 현재 값과 같아야 한다.
- OPEN 상태, 시작 전, 해석 가능한 작업지 시간대·예정 시작 시각이어야 한다.
- 확정 인원 기준 남은 자리가 있어야 한다. 지원 대기 인원은 정원에서 차감하지 않는다.
- 본인의 현재 지원 대기 또는 유효한 확정 근무가 있으면 거절한다.
- 한 날짜라도 실패하면 지원·이전 회차 전환·성공 요청 기록을 모두 저장하지 않는다.

접수 시각은 전체 잠금·검증 조회가 끝난 서버 시각 한 번을 사용한다. 마이크로초 UTC로 저장하고 응답은 공고 시간대의 오프셋으로 표현한다. 신규 공고의 기존 GMT+9 정책은 유지한다.

## 재지원 이력과 조회

미선정 또는 확정 후 시작 전 취소된 근무는 다른 지원 조건도 충족하면 새 키로 재지원할 수 있다.

- 새 지원 ID와 다음 applicationRound를 생성한다.
- 이전 지원의 상태·접수 시각·확정 근무·취소/조기 종료 연결은 유지한다.
- 이전 회차의 is_current만 false로 바꾸고 새 회차를 true로 저장한다.
- DB는 일정·근로자·회차의 중복과 일정·근로자별 현재 회차의 중복을 각각 차단한다.
- APP-01 본인 지원 조회는 현재 회차만 사용한다.
- JOB-05 지원자 수는 전체 이력에서 같은 근로자를 한 명으로 집계한다.
- 확정 집계는 시작 전 CANCELLED를 제외하고 미취소·EARLY_ENDED를 포함한다. 기존 근무 완료는 자리를 비운 것으로 계산하지 않는다.

유효한 확정 근무는 과거 회차까지 확인한다. SELECTED 표시만 있고 확정 근무가 없는 행도 기존 APP-01과 같이 ALREADY_CONFIRMED로 차단한다.

고용주의 지원자 명단·선정 API는 이번에 추가하지 않는다. 후속 WORK 기능은 현재 회차의 PENDING만 선정 대상으로 삼고, 확정 직전에 같은 조건을 다시 검사해야 한다.

## DB 변경: V12

V1~V11을 수정하지 않고 V12만 추가했다. DB에는 아직 적용하지 않았다.

application 추가:
- application_round: 기존 행과 최초 지원은 1, 양수
- applied_terms_version: 기존 행은 NULL, 신규는 접수 당시 버전
- applied_at_utc: 기존 행은 NULL, 신규는 서버 UTC 시각
- is_current: 기존 행은 true, 재지원 시 과거 회차만 false
- current_marker: 현재 회차만 1이고 과거 회차는 NULL인 생성 컬럼

기존 UNIQUE(work_schedule_id, worker_id)를 회차별 UNIQUE와 현재 회차 UNIQUE로 확장한다. 과거 지원 ID와 work_assignment.application_id FK는 바꾸지 않는다. 기존 applied_at 원본은 그대로 두고, 새 API가 만든 행의 applied_at과 applied_at_utc는 둘 다 UTC로 기록한다. 기존 행의 접수 버전·UTC 시각은 현재 조건으로 채우지 않는다.

새 테이블:
- application_request_lock: 같은 근로자의 첫 요청·재요청을 직렬화하는 잠금 행
- application_receipt: 근로자·키 UNIQUE, 공고 ID, 요청 지문, 최초 응답 JSON, 서버 UTC 저장 시각

응답 JSON에는 지원 ID·일정 ID·회차·상태·접수 버전·시각만 들어가며 개인정보·세션·CSRF·서비스 토큰은 보관하지 않는다.

## 잠금과 원자성

READ_COMMITTED 트랜잭션에서 다음 순서로 처리한다.

1. 현재 DB 근로자 역할 확인
2. 근로자별 요청 잠금 확보
3. 성공 기록 확인: 있으면 내용 비교 후 최초 결과 반환
4. 새 요청은 공고 잠금 → 일정 ID 오름차순 잠금 → 현재 지원 잠금
5. 전체 검증 후 이전 회차 표시 해제·flush → 새 지원 저장·flush
6. 최초 응답 기록 저장 후 함께 커밋

실패하면 이전 회차 전환까지 롤백하도록 구성했다. 같은 키의 동시 요청은 첫 트랜잭션 완료 후 성공 기록을 다시 읽는다. 기존 일정 수정·날짜 취소와 공고 → 일정 순서를 맞췄다. 후속 선정·마감·공통 조건 수정도 이 순서를 지켜야 한다.

실제 MySQL의 잠금 경합·롤백·생성 컬럼 UNIQUE는 아직 실행 검증하지 않았다.

## 오류 응답

```json
{
  "code": "SCHEDULE_TERMS_CHANGED",
  "message": "근무 조건이 변경되었습니다. 최신 조건을 확인한 뒤 다시 지원해 주세요."
}
```

| HTTP | 코드 | 조건 |
| --- | --- | --- |
| 400 | INVALID_REQUEST | 키·ID·버전·날짜 수·중복 일정·JSON 형식 오류 |
| 401 | 기존 인증 처리 | 세션 없음 |
| 403 | WORKER_ROLE_REQUIRED | 근로자가 아님 |
| 403 | 기존 CSRF 처리 | 토큰 누락·오류 |
| 404 | JOB_POSTING_NOT_FOUND | 공고 없음 |
| 404 | WORK_SCHEDULE_NOT_FOUND | 일정 없음 또는 다른 공고 일정 |
| 409 | IDEMPOTENCY_KEY_CONFLICT | 같은 성공 키에 다른 내용 |
| 409 | SCHEDULE_TERMS_CHANGED | 조건 버전 불일치 |
| 409 | RECRUITMENT_PAUSED / RECRUITMENT_CLOSED / RECRUITMENT_CANCELLED | 모집 상태 |
| 409 | SCHEDULE_STARTED | 시작 시각 도달 |
| 409 | CAPACITY_FULL | 확정 인원이 정원을 채움 |
| 409 | ALREADY_APPLIED / ALREADY_CONFIRMED | 유효한 중복 지원·확정 |
| 409 | TIME_ZONE_UNAVAILABLE / SCHEDULE_START_TIME_UNAVAILABLE | 기존 시간 정보 해석 불가 |
| 409 | APPLICATION_STATUS_UNAVAILABLE / SCHEDULE_STATUS_UNAVAILABLE | 해석 불가 기존 상태 |
| 409 | APPLICATION_ROUND_EXHAUSTED | 지원 회차 상한 |
| 409 | APPLICATION_CONFLICT | DB 고유 제약 등 저장 충돌 |
| 415 | INVALID_REQUEST | application/json이 아닌 요청 |
| 503 | SERVICE_UNAVAILABLE | 일시적 DB 장애·잠금 시간 초과 등 |
| 500 | INTERNAL_SERVER_ERROR | 기타 내부 오류 |

성공·컨트롤러 오류 응답에는 Cache-Control: no-store를 붙인다. 실제 CSRF·익명 응답은 기존 Security 처리를 유지한다.

## 이번 확인 범위와 후속

구현만 진행하며 테스트·DB 적용·서버 실행·커밋·푸시는 하지 않는다. 컴파일 확인은 테스트 실행과 별도로 기록한다. 기존 Flyway 테스트의 최신 버전·개수·컬럼 기대값은 V12에 맞췄다.

새 지원 API의 실제 HTTP/Security, 재요청 응답 JSON, 재지원 FK·회차 UNIQUE, 동시 중복 요청, 조건 수정·마감·선정 경합, 부분 저장 없는 롤백은 후속 검증 대상이다. farm-demo 지원 화면은 아래 후속 절에 설명한다. user-web, 정식 내 지원 내역 API, 선정·확정 API는 추가하지 않는다.

운영 전 요청 기록 보관 기간·재시도 보장 기간·만료 후 처리 정책을 함께 정한다.
## farm-demo 지원·재요청·버전 충돌·재지원 화면

`/demo/job-apply`에 새 간이 화면을 추가했다. 로그인 화면의 근로자 링크와 기존 공고 상세의 ‘이 공고에서 지원할 날짜 선택’ 링크로 이동한다. `?jobPostingId=101`로 특정 공고를 바로 열 수도 있다.

### 실제 지원 흐름

1. APP-01의 목록·상세 GET으로 지원 가능 날짜와 termsVersion을 읽는다.
2. 날짜를 1~100개 선택한다. 일반 지원 버튼은 UUID v4 키와 요청 JSON을 자동 생성한다.
3. 전송 직전 새 CSRF를 조회하고 현재 근로자 계정을 다시 확인한다.
4. 실제 `POST /api/job-postings/{id}/applications`를 호출한다.
5. 지원 결과는 별도 영역에 유지하고, 상세·본인 회차 이력을 GET으로 다시 읽는다.
6. 같은 요청 재전송 버튼은 전송했던 키·일정·버전을 그대로 사용한다. 화면에서 기억하는 최초 성공 응답과 ID·회차·상태·버전·접수 시각을 비교한다.
7. 통신 실패 시 자동 재전송하거나 성공 상태를 만들어 표시하지 않는다. 같은 요청 재전송으로 결과를 확인할 수 있다.

키·요청 JSON은 이 화면의 메모리에만 보관한다. 새로고침 후에는 화면의 재전송 버튼을 위한 기억이 초기화되지만 서버의 성공 기록은 유지된다. CSRF·쿠키·인증 헤더는 진단 영역이나 기록에 표시하지 않는다.

### demo 전용 경로

- GET `/demo/job-apply`: 공개 HTML. 실제 데이터는 근로자 로그인 필요.
- GET `/demo/api/applications/postings/{id}/history`: 세션 근로자 본인 회차의 최근 500건. 과거·현재, 미선정·확정 근무·취소 연결을 표시한다.
- POST `/demo/api/applications/fixtures`: 근로자 세션·CSRF로 새 시연 데이터를 준비한다.

컨트롤러·서비스·저장소·오류 처리기는 모두 farm-demo 프로필 전용이다. 정식 APP-04 내 지원 내역이나 WORK 선정 API를 추가한 것은 아니다.

### 시연 데이터 준비

화면에서 ‘지원 · 재지원 시연용 공고 준비’를 누를 때만 JPA 트랜잭션으로 가상 공고를 만든다. 자동 시작·조회 과정에서는 데이터를 생성하지 않는다. 이 작업 중에는 버튼을 실행하거나 DB를 변경하지 않았다.

- 고용주: 기존 demo-employer. 해당 계정이 없거나 고용주 역할이 아니면 409.
- 근로자: 로그인 세션의 본인.
- 새 가상 공고에 GMT+9 기준 7·8·9일 뒤의 세 일정을 생성한다.
- 첫째·둘째 날짜는 신규 지원용, 셋째는 새 가상 NOT_SELECTED 1회차를 넣어 재지원용으로 준비한다.
- 기존 공고·일정·지원·확정 근무를 UPDATE·삭제하지 않는다.
- 같은 근로자·같은 날의 준비 요청은 동일한 시연 공고를 돌려준다. 앞서 시연한 이력은 초기화하지 않는다.
- 이 준비는 실제 고용주 선정·미선정을 처리하는 사용자 API가 아니다. 기존 지원을 미선정으로 바꾸는 경로도 없다.

### 직접 확인 순서

1. 기존 farm-demo 설정으로 서버를 재시작한다. 새 V12가 적용돼야 한다.
2. 근로자로 로그인 → 날짜 선택 지원 링크 → 시연용 공고 준비.
3. 첫째 날짜만 지원해 201을 확인하고, 같은 요청 재전송으로 200과 최초 ID·회차·접수 시각 유지를 확인한다.
4. 아직 지원하지 않은 둘째 날짜를 선택하고 ‘현재 조건으로 요청만 준비’를 누른다.
5. 별도 시크릿 창에서 demo-employer로 로그인해 `/demo/jobs`에서 해당 공고의 둘째 일정 시간을 실제 수정한다.
6. 근로자 창은 새로 조회하지 말고 ‘선택 날짜 지원’을 눌러 이전 버전으로 전송한다. 409 SCHEDULE_TERMS_CHANGED를 확인한다.
7. 최신 조건·내 이력 조회 → 둘째 날짜 재선택 → 지원하면 새 키·새 버전으로 접수한다.
8. 셋째 날짜 지원 후 이력 표에서 미선정 1회차(과거)와 새 PENDING 2회차(현재), 서로 다른 지원 ID를 확인한다.
9. 고용주 내 공고에서 지원자 수를 보면 셋째 날짜의 두 회차는 같은 근로자 한 명으로 집계돼야 한다.

버전 충돌은 실제 일정 수정으로 발생시키며 브라우저에서 버전을 임의로 바꿔 성공/실패 응답을 만들지 않는다. 같은 브라우저의 일반 탭은 세션을 공유하므로 고용주 수정에는 별도 로그인 세션을 사용한다.

### 이번 demo의 검증 범위

Java·테스트 소스 컴파일과 인라인 스크립트 문법 확인만 수행한다. 실제 브라우저·HTTP 요청·fixture 생성·DB 적용·테스트·커밋·푸시는 실행하지 않는다. 시연 준비 SQL, 본인 이력의 JPA projection, 프로필·권한·CSRF, 브라우저 요청 비교는 후속 실행 검증 대상이다.

### APP-02 리뷰 보완 — 이력 조회 타입과 보조 조회 실패 분리

- 이력 SQL은 `is_current`를 `CAST(... AS SIGNED)`로 조회한다. BOOLEAN/TINYINT(1)이 Connector/J 설정에 따라 Java Boolean으로 반환될 수 있는 경계를 피하고 기존 `int getCurrentFlag()`와 타입을 맞춘다.
- 실제 예외 스택을 확보한 것은 아니므로, 이 변경만으로 과거 특정 공고의 500 원인이 확정됐다고 보지는 않는다. 기존 V12나 개발 DB 설정·데이터는 수정하지 않는다.
- 공고 상세가 정상일 때 이력 500·연결 실패·응답 형식 오류는 이력 영역에 따로 표시한다. 날짜 선택·지원·재전송은 유지하고 '지원 이력 없음'으로 대신하지 않는다.
- POST 201/200 응답은 후속 이력 조회 실패로 실패 처리하거나 지우지 않는다. 지원 POST 결과와 이력 재조회 오류를 함께 표시한다.
- 상세 자체의 실패, 계정 변경·로그아웃, 이력의 401/403은 계속 차단하며 이전 상세·선택·키를 지운다.
- 실제 Repository와 서비스가 격리 MySQL을 통과하는 `DemoJobApplicationHistoryMySqlTests`를 추가했다. 과거/현재 0·1 매핑, 회차 보존, 근로자·공고별 범위와 빈 이력을 확인하는 통합 테스트다.
- 화면 스크립트 테스트에는 이력 실패 시 선택 유지, POST 성공 뒤 이력 실패, 통신·형식 오류, 인증 오류, 계정 전환과 상세 실패 회귀 사례를 추가했다.

이번 보완에서는 테스트를 실행하지 않았다. 기존 검증 보고서의 Java 310개·화면 18개 통과는 수정 전 실행 기록이며, 추가 테스트와 수정 후 화면의 통과 결과를 의미하지 않는다. 새 통합 테스트는 다른 검증 담당자가 Testcontainers 격리 MySQL에서 해당 클래스만 선택해 재검증할 수 있다.

# JOB-07 날짜 모집 취소 API

고용주가 확정자가 남아 있지 않은 날짜 하나의 모집을 취소한다. 개인별 확정 근무의 취소·조기 종료, 확정자가 남은 날짜의 일괄 작업 취소와는 별도 기능이다.

## 요청

```http
POST /api/job-postings/101/schedules/201/cancel
Content-Type: application/json
X-CSRF-TOKEN: 로그인 후 발급받은 현재 토큰
Cookie: FARMSESSION=로그인 세션
```

```json
{
  "expectedTermsVersion": 1
}
```

공고·일정 ID와 조건 버전은 내 공고 조회 응답의 값을 사용한다. 버전은 필수 양의 JSON 정수이며 소수·문자열은 거부한다. 고용주 ID·취소 시각·취소 상태는 요청으로 지정하지 않는다.

## 성공 응답

```json
{
  "jobPostingId": 101,
  "workScheduleId": 201,
  "workDate": "2026-12-02",
  "status": "REMOVED",
  "termsVersion": 1,
  "cancelledAt": "2026-11-25T08:00:00.123456Z"
}
```

HTTP 상태는 `200`이다. 위 ID와 시각은 예시이며 실행 결과가 아니다. 새 취소 시각은 서버가 정한 UTC 값이고 오프셋이 있는 ISO 8601로 반환한다. 근무 조건을 수정하는 것이 아니므로 조건 버전과 조건 이력은 그대로 유지한다.

이미 `REMOVED`인 날짜는 역할·소유자 확인 후 `200`으로 기존 결과를 반환한다. 재요청이 시작 시각 이후에 도착하거나 요청 버전이 오래됐더라도 취소를 반복하지 않고 시각·이력을 변경하지 않는다. 최초 취소에는 현재 조건 버전이 필요하다. 기존 취소 행의 취소 시각이 비어 있다면 새로 추측해 채우지 않고 `null`을 반환한다. 기존 데이터의 시각 값을 일괄 변환하지 않는다.

## 처리 순서

1. 현재 DB의 회원 역할이 고용주인지 확인한다.
2. 양수 ID를 확인하고 본인 공고 → 해당 공고의 일정 순서로 잠근다.
3. 이미 모집 취소된 날짜라면 기존 결과를 반환한다.
4. 요청 조건 버전이 현재 버전인지 확인한다.
5. `OPEN`·`PAUSED`·`CLOSED` 상태인지 확인한다.
6. `countOccupyingAssignments`로 취소되지 않은 확정 근무가 없는지 확인한다.
7. 공고의 저장 시간대로 예정 시작 시각을 해석하고, 조회·잠금 대기 후 서버 시각과 비교한다.
8. 예정 시작보다 이전이면 상태를 `REMOVED`로 바꾸고 취소 시각을 기록한다.

예정 시작과 정확히 같은 시각부터는 시작된 것으로 판정한다. 실제 출근 여부를 확인한 결과가 아닌 예정 시각 기준의 운영 규칙이다. 신규 공고 시간대는 `GMT+9`이고, 기존의 해석 가능한 시간대는 유지한다. 시간대가 없거나 잘못됐거나 예정 시각이 DST 때문에 모호하면 임의로 보완하지 않고 거부한다.

확정 근무의 변경 기록이 없거나 `EARLY_ENDED`이면 남은 확정자로 집계한다. 모든 확정 근무가 `CANCELLED`이면 0건으로 보아 허용한다. 취소 시점이 이미 예정 시작 이후라면 전원 취소 여부와 관계없이 최초 날짜 모집 취소는 거부한다.

## 보존 범위

- 일정 행과 ID, 날짜·시간·휴게, 조건 버전·조건 이력
- 지원 행과 지원 상태·이력
- 기존 확정 근무의 약정
- 기존 개인 취소·조기 종료와 보험 변경 버전
- 같은 공고의 다른 날짜

새 `work_change`나 보험 변경 버전은 만들지 않는다. 신청자에게의 ‘모집 취소’ 표시는 후속 APP-04에서 일정의 `REMOVED` 상태와 연결한다. 확정자가 남아 있는 날짜는 개인별 취소 기록이 필요한 CHANGE-05 범위다.

## 오류 응답

오류 본문은 `{ "code": "...", "message": "...", "field": null }` 형식이다. Security 필터의 인증·CSRF 오류는 기존 처리 방식을 사용한다.

| HTTP | 코드 | 조건 |
| --- | --- | --- |
| 400 | `INVALID_REQUEST` | 공고·일정 ID가 0 또는 음수 |
| 400 | `INVALID_WORK_SCHEDULE` | 버전 누락·null·0·음수 (`field=expectedTermsVersion`) |
| 400 | `INVALID_REQUEST_BODY` | 잘못된 JSON·Content-Type·경로 ID 형식·정수 형식 |
| 401 | 기존 인증 처리 | 로그인 세션 없음 |
| 403 | `EMPLOYER_ROLE_REQUIRED` | 근로자 요청 또는 로그인 후 DB 역할 변경 |
| 403 | 기존 CSRF 처리 | 토큰 누락·오류 |
| 404 | `JOB_POSTING_NOT_FOUND` | 없는 공고 또는 타인 소유 공고 |
| 404 | `WORK_SCHEDULE_NOT_FOUND` | 해당 공고에 없는 일정 |
| 409 | `SCHEDULE_VERSION_CONFLICT` | 현재와 다른 조건 버전 |
| 409 | `SCHEDULE_NOT_CANCELLABLE` | 허용하지 않는 상태 |
| 409 | `SCHEDULE_ALREADY_CONFIRMED` | 취소되지 않은 확정 근무 또는 조기 종료 근무가 남음 |
| 409 | `SCHEDULE_ALREADY_STARTED` | 예정 시작과 같거나 이후인 서버 시각 |
| 409 | `TIME_ZONE_UNAVAILABLE` | 시간대 누락·해석 불가 |
| 409 | `SCHEDULE_START_TIME_UNAVAILABLE` | 예정 시작 누락 또는 시간대에서 단일 시각으로 해석 불가 |
| 409 | `SCHEDULE_CANCEL_CONFLICT` | DB 무결성·잠금 충돌 |

## farm-demo에서 확인하는 순서

1. `farm-demo` 프로필로 농업 서버를 다시 실행한다.
2. `/demo/login`에서 고용주로 로그인하고 `/demo/jobs`로 이동한다.
3. 공고와 날짜를 선택하고 **날짜 모집 취소**를 누른다. 확인창에는 입력 중인 날짜가 아닌 조회했던 날짜와 일정 ID가 나온다.
4. 확인창에서 동의하면 현재 CSRF 토큰을 발급받아 조회 시점의 `expectedTermsVersion`과 함께 전송한다. 폼의 미저장 근무·휴게 값은 전송하지 않는다.
5. 성공은 `200`이며 선택 목록과 상태가 ‘모집 취소’로 바뀌고 수정 입력은 비활성화된다. 응답 JSON·취소 시각(UTC)·모집 상태 전후 비교를 확인한다.
6. **취소 결과 다시 확인**으로 동일 API를 재요청해 기존 결과·최초 시각을 확인할 수 있다.

확정자가 남았거나 시작 시각이 지난 날짜도 버튼 자체는 요청을 보낼 수 있게 두어 서버의 실제 `409` 응답을 확인한다. 오래된 버전도 자동으로 갱신하지 않는다. 두 탭에서 같은 날짜를 조회한 뒤 한쪽에서 조건을 수정하고 다른 쪽에서 취소하면 `SCHEDULE_VERSION_CONFLICT`를 확인할 수 있다. 실패 시 미저장 입력을 유지하고, 사용자가 **최신 조건 다시 불러오기**를 누를 때 초기화한다.

취소 성공 후 목록 재조회가 실패해도 성공한 취소를 실패로 표시하지 않는다. 확인창에서 거절하면 취소 API를 호출하지 않는다. 화면 시연도 실제 개발 DB를 변경하므로 테스트용 날짜로 진행한다.

## 검증 인계

이 문서는 테스트 통과 보고서가 아니다. 이번 요청에 따라 테스트·서버·DB 실행은 하지 않는다.

후속 단위 테스트에서는 고정 Clock과 실제 도메인 객체로 시작 직전·정각·이후, 세 상태, 남은 확정 집계 0·양수, 소유자 조회 인자, 역할 변경, 조건 버전 충돌, 취소 시각의 UTC·마이크로초 정밀도, 재요청 시각 보존을 검증한다. 기존 조건과 조건 버전이 유지되고 개인 변경 기록을 생성하지 않는 범위도 확인한다.

실제 MySQL의 CANCELLED/무변경/EARLY_ENDED 집계·잠금·롤백과 Security 필터·세션·CSRF는 별도 통합 검증 대상이다. 후속 지원·선정 API도 공고 → 일정 잠금 순서와 모집 상태 재검사를 따라야 한다. 이 API만으로 아직 없는 선정 API와의 경합까지 검증한 것은 아니다.
